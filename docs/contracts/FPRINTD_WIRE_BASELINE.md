# Публичный D-Bus контракт fprintd

Область совместимости — системная шина, имя `net.reactivated.Fprint`, публичные интерфейсы Manager и Device и их наблюдаемое поведение для любого клиента. За основу взяты XML, реализация и тесты релиза `v1.94.5` (`b54a007`), а также снимок upstream `5731b9a`. В снимке добавлен `VerifyFingerMatched`; в XML релиза его ещё нет. Внутренние интерфейсы libfprint и форматы хранения fprintd в эту область не входят.

- [Manager XML](https://gitlab.freedesktop.org/libfprint/fprintd/-/blob/5731b9a94bbd50d4cc2bc0644affb3eb2be321fc/src/net.reactivated.Fprint.Manager.xml) и [Device XML](https://gitlab.freedesktop.org/libfprint/fprintd/-/blob/5731b9a94bbd50d4cc2bc0644affb3eb2be321fc/src/net.reactivated.Fprint.Device.xml)
- [Реализация Device](https://gitlab.freedesktop.org/libfprint/fprintd/-/blob/5731b9a94bbd50d4cc2bc0644affb3eb2be321fc/src/device.c) и [набор испытаний](https://gitlab.freedesktop.org/libfprint/fprintd/-/blob/v1.94.5/tests/fprintd.py)
- [Политика fprintd](https://gitlab.freedesktop.org/libfprint/fprintd/-/blob/v1.94.5/data/net.reactivated.fprint.device.policy.in)

## Состояние реализации

Сценарий `tools/test-linux-installed-start.sh --fprintd-contract` проверяет
выбор одного пальца из нескольких и устаревший метод удаления через частную
системную шину. Сценарий `--two-providers` проверяет два объекта устройств и
продолжение работы оставшегося устройства после отключения второго.

В адаптере есть отдельный объект и отдельное владение для каждого
аутентификатора. Он использует точный селектор регистрации и формирует
`VerifyFingerMatched` из подтверждённого результата CaroSign. Состояние
пальца доступно, когда его публикует провайдер. Для непривилегированных
клиентов проверяются действия PolicyKit с исходным уникальным именем
отправителя на шине. На системе должны быть доступны стандартные действия
`net.reactivated.fprint.device`. Пункты ниже сохраняют исходные выводы аудита
и перечень проверок совместимости.

## Методы

Manager публикуется по пути `/net/reactivated/Fprint/Manager`. Device публикуется по пути, который вернул Manager. Адаптер сейчас выдаёт один фиксированный путь `/net/reactivated/Fprint/Device/0` и выбирает аутентификатор из инвентаря. Для нескольких датчиков нужен устойчивый путь на каждый аутентификатор и единая привязка пути к устройству во всех методах и сигналах.

| Интерфейс и метод | Вход → выход | Что проверить или доделать |
|---|---|---|
| Manager.`GetDevices` | `∅ → ao` | Возвращать пути всех обнаруженных устройств. Проверить пустой список, порядок, добавление и исчезновение устройства. |
| Manager.`GetDefaultDevice` | `∅ → o` | Проверить выбор устройства и `NoSuchDevice` при пустом инвентаре. Различать отсутствие объекта и временную занятость. |
| Device.`ListEnrolledFingers` | `s → as` | Реализован. Проверить вызов без `Claim`, текущего и явно указанного пользователя, пустой результат, неизвестного пользователя и разные устройства. |
| Device.`DeleteEnrolledFingers` | `s → ∅` | Отсутствует. Устаревший метод остаётся публичным. Upstream допускает вызов без `Claim` при соблюдении политики и отсутствии конкурирующей работы. |
| Device.`DeleteEnrolledFingers2` | `∅ → ∅` | Реализован для владельца. Проверить отсутствие записей, частичный результат, отмену и повтор. |
| Device.`DeleteEnrolledFinger` | `s → ∅` | Реализован. Проверить точную цель, отсутствие записи, ошибки хранилища, удаление при текущей проверке и освобождение устройства после отказа. |
| Device.`Claim` | `s → ∅` | Реализован с проверкой UID. Сверить разрешения upstream, повторный вызов и конфликт владельцев. |
| Device.`Release` | `∅ → ∅` | Реализован. Сверить завершение операции, ошибку чужого клиента и момент, когда доступна новая выдача. |
| Device.`VerifyStart` | `s → ∅` | Работает `any` и запрос единственной готовой записи по имени. Не хватает точного выбора записи из нескольких, `VerifyFingerSelected` и различимых отказов. |
| Device.`VerifyStop` | `∅ → ∅` | Реализован. Сверить отмену, вызов после терминального статуса, повторный вызов и немедленный следующий старт. |
| Device.`EnrollStart` | `s → ∅` | Реализован. Сверить десять имён пальцев, занятость, повторную регистрацию, число этапов и специфические исходы. |
| Device.`EnrollStop` | `∅ → ∅` | Реализован. Сверить отмену в подготовке, во время захвата и после результата. При прерывании должны сработать откат и освобождение ресурса. |

Проверить `Introspect`, `Properties.Get`, `Properties.GetAll`, попытку записи свойства только для чтения и ответы на несуществующий объект, интерфейс, метод или свойство. Сейчас общий обработчик Device возвращает `PermissionDenied` и для неизвестных методов, и для ряда отказов по состоянию.

## Сигналы, свойства и статусы

| Поверхность | Уговор и текущее покрытие |
|---|---|
| `VerifyFingerSelected(s)` | Сообщает фактически выбранный палец либо `any` при идентификации по набору. В адаптере отсутствует. |
| `VerifyFingerMatched(s)` | Сообщает имя фактически распознанного пальца. Адаптер отправляет сигнал для сценария с единственной готовой записью. Для нескольких записей нужна подтверждённая идентичность совпавшей записи. |
| `VerifyStatus(s,b)`, `EnrollStatus(s,b)` | Адаптер отправляет адресованные сигналы. Проверить получателя, порядок относительно ответа Start и сигнала о совпадении, флаг `done`, отсутствие статусов от предыдущей операции и порядок Stop → Start. |
| `name(s)`, `scan-type(s)` | Сейчас константы `CaroSign` и `press`. Полный интерфейс должен отображать имя конкретного устройства и различать `press` и `swipe`. |
| `num-enroll-stages(i)` | Есть публикация числа этапов и `PropertiesChanged`. Сверить изменение при захвате и освобождении устройства, `-1` без захвата и обновление при смене возможностей. |
| `finger-present(b)`, `finger-needed(b)` | Сейчас всегда `false`. Нужны фактические переходы и `PropertiesChanged`, включая сброс после Stop, завершения и отключения. Активная операция сама по себе не устанавливает наличие пальца. |

Имена пальцев образуют десять значений с префиксами `left-` и `right-`. `any` допустим для VerifyStart и VerifyFingerSelected. Результаты проверки включают `verify-match`, `verify-no-match`, `verify-retry-scan`, `verify-swipe-too-short`, `verify-finger-not-centered`, `verify-remove-and-retry`, `verify-too-fast`, `verify-disconnected`, `verify-unknown-error`.

Для регистрации проверить `enroll-completed`, `enroll-failed`, `enroll-stage-passed`, `enroll-retry-scan`, `enroll-swipe-too-short`, `enroll-too-fast`, `enroll-finger-not-centered`, `enroll-remove-and-retry`, `enroll-data-full`, `enroll-duplicate`, `enroll-disconnected`, `enroll-unknown-error`. Промежуточные статусы и терминальные причины проверяются отдельно. В адаптере часть причин сводится к общему повтору или ошибке.

## Ошибки и права

Для каждого метода сверить применимые ошибки по XML и upstream-тестам: `AlreadyInUse`, `ClaimDevice`, `Internal`, `PermissionDenied`, `NoEnrolledPrints`, `FingerAlreadyEnrolled`, `NoActionInProgress`, `InvalidFingername`, `NoSuchDevice`, `PrintsNotDeleted`, `PrintsNotDeletedFromDevice`. Префикс — `net.reactivated.Fprint.Error.`. Причина отказа должна сохраняться от слоя, который её установил.

Upstream различает разрешения PolicyKit `verify`, `enroll` и `setusername`. Пустое имя разрешается в пользователя исходного отправителя D-Bus. Проверка UID в адаптере и политика CaroSign остаются действующими. Для совместимости с правилами PolicyKit потребуется привязка разрешения к исходному отправителю и конкретному действию. Привилегии процесса адаптера сами по себе не дают клиенту доступ к чужой записи. Проверить исчезновение владельца, конфликт клиентов, ошибку или отмену во время запуска и доступность ресурса после каждого исхода.

## Порядок реализации и приёмка

1. В адаптере зафиксировать XML, ввести различимые ошибки, дописать устаревшее удаление и покрыть переходы владения. Проверять подписи и ответы на частной D-Bus шине как публичный клиент.
2. Привязать объекты к аутентификаторам, включая раздельные операции, свойства и отключение устройства. Проверить инвентарь из нуля, одного и двух устройств, параллельную работу и замену устройства.
3. Выделить недостающие общие данные CaroSign: точный селектор записи при проверке, подтверждённую ссылку на совпавшую запись для уполномоченного клиента и достоверное состояние захвата. Сейчас терминальный ответ проверки сообщает итог фактора, а обратная связь захвата включает подсказку, повтор или прогресс. Дополнения согласовать в терминах регистрации и захвата. Имена пальцев и D-Bus остаются в адаптере, сигналы сенсора остаются в провайдере.
4. Подключить выбор и идентификацию, свойства захвата, полную трансляцию промежуточных и терминальных причин. Проверить последовательность успешных, ошибочных и оборванных запросов, а также повтор после удаления и отмены. Не выводить выбранный или распознанный палец из непроверенных данных.
5. Сверить поведение с upstream-тестами и прогнать штатные `fprintd-list`, `fprintd-verify -f …`, `fprintd-enroll`, `fprintd-delete` на отдельной шине. GNOME, другие оболочки и PAM fprintd — дополнительные клиентские пробы. Полнота определяется покрытием публичного контракта.
