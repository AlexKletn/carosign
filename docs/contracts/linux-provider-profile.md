# Системный профиль провайдера Linux

Этот формат описывает реализованный режим прямого запуска. Режим обнаружения
независимо запущенных провайдеров описан в [документе 06](../specs/engineering/implementation-v06/06-provider-host-and-wire.md#linux-provider-rendezvous).

Путь к профилю задаётся в настройках `carosignd` строкой
`provider_profile=/etc/carosign/provider.conf`. Сам файл настроек,
профиль, политика, исполняемые файлы и их родительские каталоги должны быть
защищены системным администратором: владелец root, запись другим запрещена.

Профиль объявляет один системный аутентификатор:

```text
broker=/usr/bin/carosign-broker
provider=/usr/lib/carosign/provider
provider_uid=987
provider_gid=987
package=01010101010101010101010101010101
profile=02020202020202020202020202020202
authenticator=03030303030303030303030303030303
resource=04040404040404040404040404040404
modality=fingerprint
```

Поле `modality` принимает `fingerprint`, `face`, `iris` и `voice`.
Демон сверяет модальность с объявлением провайдера и повторно с ответом
на привязку. В текущем Linux-выпуске выполнение операций включено для
отпечатка пальца. Остальные типы можно объявлять в каталоге устройств.

UID/GID и идентификаторы в примере — только образец, их нужно заменить
значениями установленного провайдера. Если пакет провайдера создаёт системную
учётную запись, используйте её UID/GID (например, посмотрите `id provider-user`).
Иначе администратор создаёт отдельную системную группу и непривилегированного
пользователя средствами дистрибутива и указывает их фактические числовые UID
и GID из `id`; эта платформа учётную запись провайдера не создаёт. Имена,
идентификаторы и доступ к аппаратному ресурсу определяет пакет провайдера,
а не приведённый здесь пример. Работник запускается под заданными UID/GID;
посредник и демон обеспечивают связь. Это объявление не подтверждает
аппаратный уровень защиты и не создаёт регистрацию пользователя.

Для провайдера с одним ресурсом можно дополнительно указать **оба** поля:

```text
resource_path=/абсолютный/путь/к/ресурсу
resource_role=device
```

Роль `device` задаёт символьное устройство с владельцем root, открываемое для
чтения и записи; `config` — обычный файл с владельцем root, открываемый только
для чтения и защищённый от записи группой и остальными. Родительские каталоги
должны принадлежать root и не допускать такой записи; символические ссылки
не разрешены. Идентификатор ресурса задаётся полем `resource` выше. При
действующей исключительной выдаче посредник открывает ресурс и передаёт его
дескриптор провайдеру при Bind. Оба поля можно опустить, если провайдеру
дескриптор не нужен.

Для дополнительных ресурсов после основного можно повторить поле:

```text
resource_extra=05050505050505050505050505050505:config:/абсолютный/путь/ко/второму/ресурсу
```

Формат — идентификатор из 32 шестнадцатеричных цифр, роль и абсолютный путь,
разделённые двоеточиями. Идентификаторы не должны повторяться; всего допускается
не более восьми ресурсов. Каждый входит в общую исключительную выдачу, а
посредник проверяет полный набор до передачи дескрипторов. Дополнительный
ресурс разрешён только вместе с `resource_path` и `resource_role` основного.

Для подключения `device` профиль должен явно выбрать защищённый
исполняемый файл владельца и его договор:

```text
resource_owner=/usr/lib/carosign/resource-owner
resource_owner_contract=exclusive_quiescence_v1
```

Администратор выбирает этот договор только для владельца, который до передачи
дескрипторов эксклюзивно захватывает весь набор ресурсов и при уборке
подтверждает остановку аппаратной операции и отзыв всей выдачи. Доверенная
граница включает root, supervisor, защищённые файлы и
отсутствие другого привилегированного владельца аппаратуры. Ответ об отзыве не
является результатом операции или подтверждением мутации. `config` и профили
без дескрипторов не требуют этого договора.

### Ресурс под управлением владельца

Профиль может объявить эксклюзивный ресурс, который открывает и удерживает
сам доверенный владелец. К остальным обязательным полям профиля добавляются:

```text
resource=04040404040404040404040404040404
resource_mode=owner_managed
resource_owner=/usr/lib/carosign/resource-owner
resource_owner_contract=exclusive_quiescence_v1
```

В этом режиме поля `resource_path` и `resource_role` основного ресурса
отсутствуют. Дополнительные ресурсы `resource_extra` допускаются только с
ролью `config`. Они входят в область аренды, а посредник сам открывает их
и передаёт работнику как защищённые снимки конфигурации.

Владелец получает идентификатор основного ресурса в `--resource-0`. Он
захватывает ресурс только после `Prepare` с проверенной областью аренды.
`Prepare.slots` и `Prepared.slots` пусты, а ответ не содержит
`SCM_RIGHTS`. Если нужен отдельный обмен между владельцем и работником,
профиль может включить существующий `resource_owner_worker_channel`.
Платформа проверяет аренду и освобождение ресурса независимо от того, как
владелец обращается к устройству.

### Устойчивое ограждение и готовность

Для проверки восстановления можно отдельно создать хранилище ограждений
командой `carosignd init-resource-fences /защищённый/путь/fences.redb` от
root и указать его в настройках службы полем `resource_fence_store`. При
запуске служба открывает существующий файл и восстанавливает ограждения до
запроса ресурсов; отсутствие, повреждение или подмена файла останавливают
запуск. Файл не создаётся автоматически и не является основной базой v4.
Для `device` и `owner_managed` хранилище обязательно. Ограждение записывается до Bind и
снимается только после подтверждения завершения аппаратной операции, отзыва
эксклюзивной пары и завершения процессов. При потере ответа или ошибке
ограждение сохраняется. Это подтверждение не определяет исход мутации: её
результат и восстановление учитываются отдельно в журнале платформы.
При отмене или истечении срока supervisor запрашивает эту уборку по отдельному
приватному каналу до остановки broker и владельца. Полученное подтверждение
привязано к исходной области; при гонке с обычной уборкой запрос не создаёт
второго подтверждения. Работник запускается без capabilities и с
`no_new_privs`; доверенный владелец запускается отдельно.
Пока уже допущенный вызов завершается, `Draining` опрашивается с интервалом
10 мс в пределах общего срока 5 с и не более 512 раз; каждый запрос получает
новый идентификатор. Истечение срока, исчерпание попыток или потеря ответа
сохраняют ограждение.
При старте возможности устройства берутся из декларации провайдера без
аппаратной выдачи. Такая декларация не подтверждает готовность железа:
профиль с аппаратной выдачей или арендой владельца показывается недоступным, пока платформа не получит
отдельное подтверждение готовности. Пустой или неизвестный набор операций
также не делает устройство доступным.

Полный изолированный сценарий регистрации, проверки и удаления прошёл с
моком и конфигурационным файлом. Проверка конкретного оборудования и его
адаптера описывается в документации соответствующего провайдера.

Политика по умолчанию читается из `/etc/carosign/policy.conf`.
После её изменения службу нужно перезапустить: старый снимок отзывается.
Например, правило ниже разрешает доверенному root-клиенту проверять,
регистрировать и удалять биометрию субъекта с системным UID 1000:

```text
uid=0 subject=1000 actions=verify,enroll,remove purpose=session-login lifetime=30
uid=0 subject=0 actions=inventory
```

Право читать инвентарь задаётся отдельно действием `inventory` в правиле
с `uid=UID subject=UID`. Если для этой пары уже есть правило, добавьте
`inventory` к его `actions`. Это разрешение необходимо и для UID 0,
включая системные клиенты PAM и fprintd, которые выбирают устройство по
инвентарю.

Для запроса состояния операции (`GetOperation`, команда
`carosignctl status`) добавьте `observe` в правило вызывающего для
субъекта этой операции. Например, `uid=0 subject=1000 actions=observe`
разрешает root читать состояние операций субъекта 1000. Если правило для
этой пары уже есть, добавьте действие к его `actions`. Достаточно прав
наблюдения за субъектом, право чтения списка устройств проверяется отдельно.

Запрос `ObserveOperation` использует то же действие `observe`.
Служба отвечает снимком с ID запроса, затем отправляет сохранённые и новые
события без ID запроса. При вытеснении истории `EVENT_GAP` содержит снимок
и его номер, с которого продолжается поток. Для наблюдения используйте
отдельное соединение. Живая подписка действует до завершения операции или
до 60 секунд. При переподключении передайте последний обработанный номер.
После перезапуска, когда остался только журнал мутации, служба возвращает
снимок без истории событий.

Число одновременных живых подписок на операцию регулируется
`observers_per_operation` в `carosignd.conf`. По умолчанию 8, допустимы
значения от 1 до 32. При исчерпании лимита следующая подписка получает
`LIMIT_EXCEEDED`. После закрытия подписки место освобождается.

Параметр `queued_per_authenticator` ограничивает число ожидающих запросов
на один аутентификатор. По умолчанию 16, диапазон от 0 до 64. Ноль отключает
ожидание при занятом устройстве. При заполнении очереди служба возвращает
`BUSY`. Запрос ожидает до 15 секунд в рамках срока своего разрешения,
до `OperationAccepted` и запуска работника. Разрыв соединения или отзыв
права освобождает место. Общее число одновременно обслуживаемых запросов
также ограничено числом рабочих потоков службы.

Для отмены с отдельного системного соединения (`CancelOperation`,
`carosignctl cancel`) добавьте `cancel` в правило вызывающего для субъекта
операции. Исходный владелец может отправить отмену по своему соединению.
Квитанция `REQUESTED` означает, что отмена принята к обработке. Итог
отката или необходимость сверки определяются отдельно. Авторизованный
запрос к завершённой операции получает `ALREADY_TERMINAL`.

Замените UID субъекта фактическим значением `id -u ИМЯ`; разрешать действия
следует только тем клиентам и субъектам, которым они нужны. Для проверки
нужны подходящая регистрация в хранилище и совместимый провайдер.
Регистрация и удаление прошли сквозное испытание с тестовым провайдером;
для реального провайдера требуется отдельная проверка. Пример не устанавливает
и не включает PAM.

## Обнаружение публикаций Linux

Если `provider_profile` отсутствует, `carosignd` сверяет публикации при
запуске и при изменении путей публикации. Потеря событий запускает полную
сверку и обновление привязок. Перед выдачей инвентаря или выбором исполнителя
служба повторно проверяет текущее состояние. Отсутствующий
список разрешений означает пустой каталог. Защищённый файл
`/etc/carosign/providers.conf` задаёт по одной записи на строку,
разделяя поля пробелами:

```text
example-fingerprint 987 987 03030303030303030303030303030303 /etc/carosign/fingerprint.conf
example-fingerprint 987 987 05050505050505050505050505050505 /etc/carosign/second-fingerprint.conf
```

Поля задают имя каталога публикации, выделенные UID и GID,
`AuthenticatorId` и абсолютный путь к защищённому профилю исполнения.
Имя состоит из ASCII-букв, цифр, дефиса и подчёркивания. Для каждого устройства
нужна отдельная строка. Строки с одинаковым именем публикации должны иметь
одинаковые UID и GID. UID принадлежит только одной публикации, а
`AuthenticatorId` уникален во всём списке. Допускается до 64 устройств.
Для устройства без профиля исполнения указываются четыре поля. После
публикации его описание отображается в инвентаре со статусом «недоступен».

Чтобы временно отключить устройство, администратор добавляет `disabled` в
конец его строки через `sudo carosign-config edit providers`:

```text
example-fingerprint 987 987 03030303030303030303030303030303 /etc/carosign/fingerprint.conf disabled
```

Флаг можно указать и сразу после ID у устройства без профиля исполнения.
Отключённое устройство остаётся в инвентаре, даже если провайдер временно
его не публикует. Служба отклоняет новые операции для этого ID и пропускает
его при проверке готовности. Другие ID той же публикации обрабатываются
обычным образом. Удаление флага снова разрешает штатную проверку и работу
устройства. Для изменения списка публикаций перезапуск службы не требуется.
То же действие доступно в раскрытой карточке через PolicyKit. Для
автоматизации администратор может вызвать
`carosign-config device-admin disable ID` или
`carosign-config device-admin enable ID`, передав полный 32-значный
шестнадцатеричный ID.

Демон провайдера отвечает на запросы `Describe` и `OpenSession`
по `/run/carosign/providers/<имя>/control.sock`. Каталог
публикации и сокет принадлежат указанным UID/GID, общий каталог принадлежит
root. Платформа сверяет владельцев, учётные данные подключённого демона
и каждый идентификатор аутентификатора с защищённой конфигурацией.
`Describe` может вернуть любое подмножество разрешённых устройств. Ответ
с неизвестным или повторяющимся ID отклоняется целиком. Сеанс открывается
для одного ID и использует профиль из его строки. После потери
наблюдавшейся публикации запись становится недоступной, а новая
публикация получает новую эпоху.

Профиль исполнения задаёт брокер, идентификаторы и ресурсы. Значение
`provider=` проверяется при чтении профиля и используется при запуске
в режиме явного `provider_profile`. В режиме обнаружения отдельного
работника на каждый `OpenSession` запускает демон провайдера. Платформа
передаёт его проверенный канал брокеру и наблюдает завершение процесса
через pidfd. Политика клиента, выдача ресурсов, журнал и подтверждение
уборки используются и в режиме обнаружения.

Проверка, обычная регистрация и удаление доступны по этому пути. Для
профилей с `resource_owner_worker_channel` демон провайдера должен передать
работнику флаг `OpenSession.owner_channel_required`. Работник после
`WorkerProof` принимает и подтверждает закрытый канал до `WorkerHello`.
В Rust для этого доступна функция
`carosign_linux_ipc::provider_rendezvous::receive_owner_channel`.
Для обнаруженного аппаратного профиля нужны `resource_fence_store` и
владелец ресурса с договором `exclusive_quiescence_v1`. После объявления
возможностей служба отдельно проверяет `BindAuthenticator` через брокер.
Устройство становится доступным только после подтверждённого освобождения
выдачи. Результат действует для текущей эпохи и защищённого профиля.
Ошибка или неподтверждённая уборка оставляют устройство недоступным.
Чтение инвентаря регулируется тем же действием `inventory`.

В клиентском инвентаре платформа может указать код причины недоступности
устройства. Код относится к текущей публикации и эпохе устройства. Результат
проверки готовности действует только пока актуальны проверенная привязка и
профиль исполнения. Поле `unavailability_reason` в ответе провайдера должно
оставаться незаполненным. Клиент трактует отсутствующий или неизвестный
код как недоступность без уточнения причины.

Изолированная проверка этой проводки запускается командой
`sh tools/test-linux-installed-start.sh --discovered`. В ней публикация
появляется, снимается и восстанавливается без перезапуска `carosignd`.
Регистрация, проверка и удаление выполняются через независимый тестовый
демон провайдера.

Режим `sh tools/test-linux-installed-start.sh --two-providers` проверяет
работу двух независимых тестовых провайдеров в одном экземпляре
`carosignd`, включая отказ публикации с чужими учётными данными и
операции на оставшемся устройстве после снятия первой публикации.

В режиме `sh tools/test-linux-installed-start.sh --sudo` сценарий запускает
настоящий `sudo` от непривилегированного пользователя в изолированном корне.
Проверяются вход по отпечатку без ввода пароля, отказ без обоих факторов
при остановленном провайдере и вход через тестовый запасной модуль PAM.

### Восстановление ограждения после перезапуска

Профиль с эксклюзивным владельцем может указать защищённый исполняемый файл
`resource_recovery_owner=/абсолютный/путь`. Платформа вызывает его под
идентичностью `carosignd` с очищенным окружением и закрытым stdin, пока обычная
выдача ресурса заблокирована. Вызов возможен только при точном совпадении
аутентификатора и полного набора ресурсов с сохранённой областью.

```text
recover-resource-v1 --reason unconfirmed-release --boot BOOT
  --operation OPERATION --lease LEASE --worker WORKER
  --authenticator AUTHENTICATOR --epoch EPOCH
  --resource ID:MODE [--resource ID:MODE ...]
```

`BOOT` обозначает текущую загрузку, `EPOCH` — эпоху исходной выдачи.
Идентификаторы представлены 32 строчными шестнадцатеричными цифрами.
Режим ресурса — `exclusive`, `shared-read` или `mediated`.
Владелец проверяет область запроса и завершает процесс с кодом 0 только
после подтверждения аппаратного покоя всех ресурсов и исключения
возобновления прежнего доступа. Владелец не оставляет фоновых процессов
и учитывает повторные вызовы. При неопределённом результате он возвращает
ненулевой код и может записать причину в stderr службы.

После успешного ответа платформа удаляет точную область одной устойчивой
транзакцией. При отказе, таймауте или ошибке транзакции планировщик удерживает
ограждение. Ограждения старого формата без области требуют отдельной сверки.
Исход операции регистрации остаётся предметом проверки журнала мутаций.
