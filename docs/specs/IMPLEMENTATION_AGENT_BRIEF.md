10. **Новые жёсткие правила v0.6.2 (B-01/B-02):** verified desired *или* unchanged pre-state всегда переходят `Reconciling → Committing → Finalizing → Terminal`; первый случай меняет Registry CAS, второй не меняет enrollment/index, но атомарно фиксирует журнал NoChange. `MetadataFailed` после arm → reconciliation/quarantine, даже если commit ACK потерян; StorageUnavailable при невозможности сохранить эту отметку. Verify без `DispatchArmed`: `VerifyDispatchNotSent` → typed failure, `VerifyDispatchUnknown` → suppress result + quiesce/quarantine. `MUTATION_COMPLETED` обязан иметь `terminal_outcome` (Committed/NoChange), другие фазы — UNSPECIFIED. Выполни B-01a..f / B-02a..f. Не выбирай другие переходы.

11. **Жёсткое решение v0.6.3:** Machine определяется ТОЛЬКО `OperationBody::{Verification,Enrollment,Removal}`, не `mutation.is_some()`. Запрещено независимо хранить ещё один mutable `kind` внутри Engine. `SendVerify` и `SendMutatingCommand` имеют непересекающиеся typed receipts. Чужое подтверждение => InvalidInputForOperation без эффекта. `Enroll(replace)` сравнивает полные pre/desired; partial => Indeterminate. До v0.6.5 формат плана был блокером; теперь plan в storage v2 строго по документу 33, не генерировать альтернативную схему. Отсутствие independent physical query остается блокером. Тесты E-08..E-14.

12. **Нормативное решение v0.6.4 — matching существует ТОЛЬКО в провайдере.** Прочитай `engineering/implementation-v06/29-v064-provider-owned-matching.md` прежде чем менять Core/Engine/Runtime. Не создавай generic `Matcher`, `Capture`, `score`, `template` в Core/Runtime. `StartVerification` требует текущие разрешённые `EnrollmentBinding` (provider.proto minor=2). No-token Matched порождает ограниченный ProviderAssertion и не аппаратный proof. Матчинг без контроля SubjectRef scope запрещён. `template_blobs` — опциональный storage vault для провайдера, а не общая обязательная схема обработки. Не реализуй vault broker без отдельного ADR. Тесты M-01..M-12.

13. **Новое v0.6.5 (B-10, B-11…13, A-15):** неизменно исполняй 30–33. HAT-required enrollment: audited pre-enroll challenge → trusted credential authority → scoped authorization ref; ни сырых токенов в worker-control, ни test-enroll bypass. `StartRemoval.enrollment_binding` обязательно и scoped. Broker v1.1 даёт **только** typed mediated `Call.external_body` с одним sealed memfd на broker channel (не provider-control). Trusted handler удерживает DMA до подтверждённого hardware completion; без проверенного устройства STOP. Все новые мутации требуют persisted logical `MutationRecord.plan` schema 2 до dispatch; это не аппаратное подтверждение. Выполни H-01..10, L-01..14, R-01..10, S-01..03; отсутствующие проверки помечай NOT RUN. Перепроверяй Provider v1.2, Broker v1.1, existing client v1.0. Goodix safe independent query НЕ доказан.

14. **v0.6.6 B-14: обязательное решение перед реализацией Enroll.** `engineering/implementation-v06/34-v066-enrollment-command-projection.md` is first-read normative. `CommandPlan` is a validated Runtime projection from durable plan v3 plus scope-locked exact Registry binding. `MutationChange::Enrollment` has `Create(planned_new)` or `Replace(planned_new, old_binding)`; NEVER both fields absent.
