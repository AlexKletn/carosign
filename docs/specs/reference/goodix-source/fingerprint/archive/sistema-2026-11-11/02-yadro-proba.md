# 02 — Ядро: proba (загрузка приложения, питание, IRQ)

Файл: `linux-rom/fingerprint/proba/spinel_fp_proba.c` (2492 строки) ✅SRC.
Значение: **владелец** доверенного приложения и всей железной части датчика.
Без него ни один путь (наш или HAL) не работает. Это самая «пробная» часть
кода: десятки `module_param` — следы разборов, а не рабочий договор.

## Ступени (`stupen`)

| ступень | что делает |
|---|---|
| 0 | привязка и печать |
| 1 | область памяти из дерева (`spinel-fp-region`) |
| 2 | выделение в ней места |
| 3 | сборка образа `goodixfp` из `/firmware/image` |
| 4 | мост разделяемой памяти (shm bridge) |
| 5 | запуск приложения |
| ≥7 | склад tzmem под посылки |
| ≥8 | пробуждение сенсора (`razbudit`) |
| `load_keep=1` | загрузка + питание + IRQ + отдан шиму, модуль остаётся |

✅SRC `load_keep` возвращается **раньше** `stupen ≥ 8`, поэтому пробуждение
вызывается прямо в ветке `load_keep` — иначе сенсор остаётся без питания и
`DETECT_SENSOR` даёт `1062`.

## Сборка образа (`spinel_fp_sobrat`) ✅SRC

* `.mdt` и куски `.bNN` кладутся **по файловым смещениям**, не по `p_paddr`:
  подпись считана с файла, и среда проверяет именно байты в этих отступах.
* Оба разряда ELF: `cmnlib` — ELF32, `cmnlib64` и приложение — ELF64.
* Длина склейки = размер `.mdt` + сумма размеров кусков (`goodixfp` 7 655 266).

## Порядок запуска ✅SRC (и ✅MSR — расхождение, см. ниже)

1. `cmnlib64` — только проверка `app_get_id`, печать `loaded / NOT loaded`.
2. `app region` (до библиотек): `qseecom_set_app_region(0x82400000, 0x3a00000)`.
3. Свой буфер 2 МиБ под библиотеки + **свой** shm bridge.
4. `load_services` для `cmnlib` и `cmnlib64` (команда 7).
5. `load_services` для образа приложения (для проверки).
6. `app_get_id(app)`: если известен — приложение «доступно», конец.
7. Иначе: `app_start("cmnlib64", lib_phys, …)`, затем `app_start(app, obraz_phys, mdt_len, img_len)`.
8. `load_keep`: пробуждение сенсора, netlink, IRQ, `load_km` (при `load_km=1`).

⚠️ Наш Rust-клиент **не должен** ничего из этого повторять: приложение уже
загружено proba, и Rust лишь берёт его id через `LOAD_APP` шима.

## Железо: питание и прерывание ✅SRC

* `spinel_fp_hw_wake()`: регулятор `vdd` (3 000 000 мкВ), сброс через GPIO
  (`gpiod_set_value_cansleep`), тайминги 40 / 10 / 3 мс.
* IRQ-линия — свойство `irq`, регистрация `request_threaded_irq` с
  `IRQF_TRIGGER_RISING | IRQF_ONESHOT`, имя `spinel-fp`.
* Обработчик `spinel_fp_irq_nl`: считает `tychki`, `complete(tychok)`,
  зовёт счётчик (если поднят `spinel_fp_irq_count`) и **шлёт netlink**.

## Netlink: доставка события потребителю ✅SRC

* Unit **29**, `netlink_kernel_create`, payload 4 байта, `payload[0] = 1`
  (`GF_NET_EVENT_IRQ`).
* Получатель — по **портиду**. Стоковый HAL регистрируется сам: шлёт первое
  сообщение, `nlmsg_pid` запоминается. Наш Rust этого не делал — события
  уходили старому получателю. Исправлено: `GF_IOC_INIT` в заглушке зовёт
  `spinel_fp_nl_owner_set(pid_nr(task_tgid(current)))`.
* Перед отправкой протухшие сообщения получателя выбрасываются
  (`skb_recv_datagram(MSG_DONTWAIT)`), иначе первый край → событие о прошедшем
  касании.
* Прореживание `nl_ms` (по умолчанию 40 мс): края чаще отбрасываются. Счётчик
  `spinel_fp_irq_count` ведёт учёт **до** прореживания.

✅MSR На холостом кристалле (питание, сброс, `INIT`, без `1010`) — **ноль**
краёв за 90 с. Значит события появляются только в сеансе распознавания.

## Загрузка keymaster (путь B, `load_km=1`) ✅SRC

`km41` — единый подписанный образ keymaster64+gatekeeper; грузится
`app_start("keymaster64", phys, mdt=0x3000, img=размер)`, id отдаётся шиму
как `spinel_km_app_id`. Сначала — `app_get_id` по именам
(`keymaster64`, `gatekeeper`, `qcom.tz.keymaster64`, …): грузить заново
загруженное нельзя.

## Известные помехи

⚠️ `cmnlib64: NOT loaded (rc=-2)` и `set app region (before libs): -22`
встречаются и в удачных загрузках (там `-22` у региона и всё равно
`app 'goodixfp' LOADED, id=5`), и в неудачных (`app_start failed: -22`).
Исход плавает — это **не** доказанная причина, но именно сюда смотрит
следующий разбор.
