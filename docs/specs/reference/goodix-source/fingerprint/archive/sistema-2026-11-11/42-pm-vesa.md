# 42 — Пробел №3: `ASPDLWeight…PM` — это чьи веса и для чего

Закрывает пункт 3 из [40](40-chto-ostalos.md). Ранее стояло «вероятно,
калибровка — но догадка». Теперь — по коду.

## 42.1 Четыре символа, 189 716 Б каждый ✅BIN

| символ | адрес | размер |
|---|---|---|
| `ASPDLWeightLight3956PM` | `0x2ce864` | 189 716 |
| `MistouchDLWeightLight3956PM` | `0x32b28c` | 189 716 |
| `ASPDLWeightLight3976PM` | `0x2fcd78` | 189 716 |
| `MistouchDLWeightLight3976PM` | `0x3597a0` | 189 716 |

⚠️ `ASPDL` ≠ `ASPDL`. В `nm` вывод показывает **`ASPDC…`** нет; проверено
`readelf -sW`: имена начинаются с `ASPDLWeightLight…` (в декомпиляции
видно как `ASPDLWeight…`). Это **не** `DLWeight…` из `1111`.

## 42.2 Где применяются ✅BIN

По релокациям ✅ у этих четырёх **нет слотов GOT** (в `.rela.dyn` их нет).
Значит код берёт их не через GOT, а **по адресу** (adrp/add), и потому это
ветви, собираемые литералом.

⚠️ Поиск `adrp/add` на эти адреса дал **ни одного попадания** — то есть в
`libgf_hal.so` (этом образе) их **никто не использует**. Это сборочный
запас: символы есть в файле, а кода, который их зовёт, нет.

## 42.3 Что это значит

* `1111` (модель фильтра) — только `DLWeight…`, как и записано в
  [41](41-vesa-dlya-0x2e.md) ✅;
* `ASPDL…PM` — **не нужны нашему пути вовсе**, и не «вероятно калибровка»,
  а: **в образе лежат, никем не вызываются** ✅.

⚠️ Для `1064`/`1102`/`1103` (испытательные) тела готовит приложение TZ, а
не HAL — это уже видно по тому, что тела там нулевые.

## 42.4 Что это меняет

Пункт 3 из [40](40-chto-ostalos.md) закрыт: **веса `PM` к рабочему пути
отношения не имеют**. Искать их назначение не нужно.
