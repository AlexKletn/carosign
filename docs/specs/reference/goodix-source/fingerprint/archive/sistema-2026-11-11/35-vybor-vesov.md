# 35 — `hal_milan_select_model`: выбор весов по чипу (правильный заход)

⚠️ **Сперва — исправление.** В [34](34-adresa-fajl-i-obraz.md) я написал,
что `.text` надо читать по файловому смещению. Это неверно для
`objdump -d` по всему файлу: `objdump` берёт адреса **из заголовков
ELF** и сам их сопоставляет. Проверено: `objdump -d libgf_hal.so` даёт
`63350: bl 65c3c <gf_hal_milan_function_customize@@Base+0x223c>` — это
и есть `hal_milan_init_model` @`0x163350`. Значит **по файлу целиком
objdump работает правильно**; ошибка была только в ручном `dd` + `--adjust-vma`.

✅ Правило простое: **читать через `objdump -d <файл>`** (или
`--start-address=…` с **адресом из `nm`**), а не резать файл руками.
(Для драйвера ядра из `Image` ручная нарезка нужна — там нет заголовков
ELF.)

⚠️ Нарезка руками тоже возможна, если пересчитать через **заголовки
программ**: `file_off = virt − 0x161a0 + 0x161a0` для `.text` неверно для
всех адресов — верно только для тех, что читались с поправкой `−0x10000`.

## 35.1 Что видно в `hal_milan_init_model` ✅BIN

```
63324  hal_milan_init_model:
63350  bl  65c3c            ← FUN_00165c3c: «наш ли это чип»
63358  cbnz w0, 63388       ← да → дальше, нет → печать «unspport chip id»
63388  … malloc 0xc3568 → select_model(вид 0) → 1111
                            → если config[0x184] → select_model(вид 1) → 1111
```

## 35.2 `hal_milan_select_model` — вид `1` ✅BIN (по строкам декомпиляции)

Для нашего чипа `0x2e`:

```
*param_2 = 0x12321;                       /* 74 529 слов = 298 116 байт */
memcpy(куда, DLWeightLightDubaiB4_3_0_0MisTouch, 0x12321 << 2);
```

Таблица символов (`readelf -sW`):

| символ | адрес | размер |
|---|---|---|
| `DLWeightLightDubaiB4_3_0_0MisTouch` | `0x1f42d8` | 298 116 |
| `DLWeightLight3966MisTouch_13_13` | `0x23cf5c` | 298 116 |
| `DLWeightMis_3976ZS` | `0x285be0` | 298 116 |
| `DLWeightLight3956Filter` | `0xd10c8` | 298 116 |
| `DLWeightLightDubaiAFilter` | `0x119d4c` | 298 116 |
| `DLWeightLightChicagoCUFilter` | `0x1629d0` | 298 116 |
| `DLWeightLightDubaiS200_116Filter` | `0x1ab654` | 298 116 |
| **`DLWeightLightDubaiB16BIT`** | `0x387cb4` | **582 580** |

## 35.3 Вывод с двумя уровнями уверенности

✅ **Доказано:** вид `1` (защита от ложных касаний) для `0x2e` — это
`DubaiB4_3_0_0MisTouch`, 74 529 слов. **Это не та модель**, что грузит
наш Rust.

⚠️ **Не доказано:** какой символ берёт **вид `0`** (основной фильтр) для
`0x2e`. Видно лишь, что путь идёт через таблицу прыжков, а её Ghidra не
развернула. Свидетельство в пользу `DubaiB16BIT` — **замер**: `1111`
с этими весами на планшете прошла ✅MSR, и размер вдвое больше
(16 разрядов вместо 8 — по названию `B16BIT`).

⚠️ Утверждение «вид 0 = DubaiB16BIT» остаётся **вероятным**, а не
доказанным, и в тексте помечено как таковое.

## 35.4 Чего не хватило

⚠️ Развернуть таблицу прыжков **не удалось**: `objdump` по файлу на
адресах `0x1635c8…0x163700` показывает **не те функции** (там уже
`gf_hal_user_invoke_command` и `gf_hal_open`), а декомпилятор Ghidra
на `hal_milan_select_model` выдаёт «Could not recover jumptable». То есть
адрес функции из декомпиляции и разметка кода в образе **расходятся** —
это ещё один повод не смешивать две системы адресов (см. [34](34-adresa-fajl-i-obraz.md)).

Как закрыть без железа:

1. В Ghidra вручную разметить `hal_milan_select_model` как функцию и
   пересобрать (`analyzeHeadless -process … -postScript` с `disassemble`).
2. Либо найти вызовы `memcpy` с `PTR_DLWeight…` в окрестности
   `0x1635c8…0x163720` поиском по байтам: `adrp/add` пар с целью в
   диапазоне символов весов.
3. Сверить имя символа с размером: `0x238ed` слов = 582 580 Б — это
   `DubaiB16BIT`.

⚠️ Всё это — разбор, без планшета.
