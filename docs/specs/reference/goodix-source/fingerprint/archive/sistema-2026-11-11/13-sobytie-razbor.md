## Прочитанное в 22:5x — что оказалось не так

1. `irq_pre_process` @`0x15cb64` **не переиспользует состояние**: он каждый
   раз обнуляет тело (`body[0x4fd4c]=0`, `body[0x4fd65]=0x02000000`,
   `body[0x4fd94]=0x200`, `body[0x4ff9c]=1`). Значит «сохраняем тело между
   вызовами» — верно только на ветке `4`/`5` внутри одного прохода.
2. Ветвление по шагу: `body[0x4ff9c] == 4` → второй `1016`; `== 5` → третий.
   Строки `GF_IRQ_STEP_GET_IMAGE` / `GF_IRQ_STEP_POST_GET_IMAGE`. Это и есть
   единственная «серия» у стока.
3. Операция `+100` в таблице `@0x15d52c` **не** «вне таблицы», как писал
   разбор раньше: туда попадает маска `+0x60`, а таблица операций другая.

Вывод, на котором исправлено: по нашему событию `[2]` (маска `0x2`) сток
**не** ждёт край — он обрабатывает его («палец внизу», `notify 0x3ea`), и
повтора `1016` нет. Значит нашему клиенту после `[2]` нужен не край, а
следующий шаг открытого обмена, и первый `1016` в сеансе — не «взведение».

## Цепочка вызовов (адреса — в образе `libgf_hal.so`)

```

  → hal_milan_an_series_irq    @0x15c9f4
      тело = malloc(0x4ffa8), memset 0

      irq_process              @0x15d52c

```

`gf_hal_irq` ✅BIN:

```c

if (!g_hal_inited) rc = 0x3f2;                 /* 1010, HAL не открыт */
else               rc = g_hal_function[0x70](); /* = hal_milan_an_series_irq */

```

⚠️ Здесь нет ни повтора, ни серии: **один вызов = одно событие**.

## `irq_pre_process` @`0x15cb64` — откуда тело

1. Мемоизация времени: `g_irq_time_milan_an = now`.
2. **Тело инициализируется с нуля каждый раз**:

```c
body[0x4fd4c] = 0;
*(u32*)(body + 0x4fd65) = 0x02000000;
*(u64*)(body + 0x4fd69) = 0;
*(u32*)(body + 0x4fd94) = 0x200;
*(u32*)(body + 0x4ff9c) = 1;            /* ступень 1 */
invoke_command(0x3f8 /* 1016 */, body, 0x4ffa8);
```

3. Если ответ оставил ступень `4` — **сразу второй `1016`** с тем же телом
   (печать `GF_IRQ_STEP_GET_IMAGE`).
4. Если ступень `5` — **третий `1016`** (`GF_IRQ_STEP_POST_GET_IMAGE`).
5. Дальше чтение маски `+96` и операции `+100`, печать `irq_type=…,
   operation=…`, время нажатия.

⚠️ Вот что я называл «серией»: она есть, но **только внутри одного вызова**
и только на ступенях `4`/`5`. На первом ответе (ступень `2`) повтора
**нет**. Значит наша правка «продолжать по шагу 4/5» была верна по существу,
а условие было завязано не на тот шаг.

`FUN_0015f880` @`0x15f880`:

```c

if (mask & 0x80) FUN_0015fad4(body, &rc);   /* изображение – главный разбор */
                        DAT_518e70 = (*rc == 0x428);   /* 1064 */
                        DAT_518e74 = (*rc == 0x44e);   /* 1102 */
```

⚠️ **Биты маски**: `0x2` нажатие, `0x80` изображение, `0x4` отпускание.
Наше касание давало `0x2` — только нажатие, без `0x80`. Поэтому основной
разбор изображения (`0x15fad4`) не запускался вовсе.

## `FUN_0015f978` @`0x15f978` — нажатие

* При маске без `0x80` (то есть при `0x2`) **сбрасывает флаги видов** и
  уведомляет `gf_hal_notify_acquired_info(0x3ea)` (1002 = «палец внизу»).
* Операция `0` — длинное нажатие: таймер `long_pressed`;
  операция `2` — уведомления 6 и 0; операции `1`, `4` — ничего.

## `FUN_0015fad4` @`0x15fad4` — разбор ответа изображения

При результате `0`: операция `0` — `enroll_success`, `1`/`2` —
`FUN_001603bc` (успех распознавания), `4` — FIDO-успех.
Коды результата: `0x3ee` — несовпадение, `0x3f3` — мало годной площади,
`0x3f4` — плохое качество, `0x3f5` — палец уже есть, `0x3fe`,
`0x402` — ошибка CRC, `0x415` — дублирующая область.

## `gf_hal_common_set_active_group` @`0x11de14` — 1014

Под мьютексом, `calloc(100)`, `+0x60 = group`, `1014`, ставит
`g_set_active_group_done = 1`.

## Что из этого следует для Rust

1. Событие с маской `0x2` — это **только нажатие**; без `0x80` распознавание
   не идёт. Нет смысла ждать «следующего края»: датчик ждёт, что хозяин
   прочтёт изображение (`1016` на `0x80`).
2. Повтор `1016` — только по ступеням `4`/`5` из ответа, один-два раза.
3. Стартовый `1016` (ступень `2`) — часть открытия, а не сеанса.
4. `1086` — четыре поля: группа, `finger_id`, операция, маска.
5. `1010` — группа, `challenge` (8 байт), состояние экрана (`-1`).

## Что ещё найдено в `irq_pre_process` (поля `+100`, `+104`, `+84`, `+0x4ff98`)

⚠️ **Разбор `irq_pre_process` по частям не закончен.** Видно, что у тела
события есть поля, которых наш разбор не знает:

| поле | что видно |
|---|---|
| `+100` | операция датчика: `0` запись, `1` распознавание, `2` быстрое, `4` FIDO, `5` база пальца, `6` навигация, `9/10/11` ключ/кнопка, `0x2b`, `0x33` тестовые |
| `+104` | «оператор» — прочитанная команда (`1064`/`1102`/`1103`), ставится в `DAT_518e70..78` |
| `+84` | результат навигации (`if operation == 6 && mask == 2`) |
| `+0x4ff98` | скорость SPI в ответе |
| `+0x4fd4c` | начало токена (`notify_authentication_succeeded`, 8 байт) |
| `+0x4fcc0`/`+0x4fcc4` | группа / `finger_id` |
| `+0x4fcd0`/`+0x4fcd1` | `save_flag` / `authenticate_update_flag` из ответа `1086` |

**Эти же поля читает уже написанный `goodix.rs`** — как раз там сейчас
стояло условие «ждать шаг 4/5» из `irq_pre_process`, а не разбор
изображения. Следующий заход — перенос `irq_pre_process` целиком (условные
повторы на `4`/`5`, флаги видов, время нажатия, `spi_speed`), затем
проверка на железе, что событие с `0x80` доходит.
