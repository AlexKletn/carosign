## 32.2 Условие входа в `hal_milan_init_model` ✅BIN

`hal_milan_init_model` @`0x163324` начинается с `FUN_00165c3c` —
`GF_CHIP_3956`-серия:

```c
chip = g_hal_config[0];                 /* тело DETECT_SENSOR +0x60 */
ok = (chip == 0x16) || (chip - 0x2b < 4) || (chip == 0x30);
```

То есть **вход разрешён для**: `22` (`0x16`), `43, 44, 45, 46`
(`0x2b…0x2e`), `48` (`0x30`). Наш `46` — проходит ✅.

⚠️ Раньше это условие стояло как «не разобрано»: теперь оно прочитано,
и оно объясняет, почему при чужом чипе модель просто не грузится.

## 32.3 `hal_milan_select_model` @`0x1635c8` — выбор весов ✅BIN

```
аргументы: (куда писать, &число_слов, вид)
вид = 0  →  основной фильтр: выбор по таблице прыжков @0x1a96f4
            (по g_hal_config[0] − 0x16; интересует диапазон 0x2b…0x30)
вид = 1  →  защита от ложных касаний:
            0x2c → DLWeightLight3966MisTouch_13_13,  0x12321 слов
            0x2e → DLWeightLightDubaiB4_3_0_0MisTouch, 0x12321 слов
            0x30 → DLWeightMis_3976ZS,                0x12321 слов
вид > 1  →  ошибка параметров
```

⚠️ Для `0x2e` (наш `3956`) вид `1` — это **DubaiB4**, а **не** DubaiB16BIT.

⚠️ **Размеры символов (`readelf -sW`, ✅BIN):** `0x12321` слов = 298 116
байт — ровно столько у `DLWeightLight3956Filter`, `DubaiAFilter`,
`DubaiB4_3_0_0MisTouch`, `3966MisTouch_13_13`, `ChicagoCUFilter`,
`DubaiS200_116Filter`, `DLWeightMis_3976ZS`. А `DLWeightLightDubaiB16BIT`
— **582 580 байт** (`0x8e3b4`), ровно вдвое больше. Значит **DubaiB16BIT —
не вид `1`**: это другая, «двойная» модель в 16 бит.

Наш Rust грузит `DLWeightLightDubaiB16BIT` с проверкой SHA-256 — и на
планшете `1111` прошла с нулевыми статусами ✅MSR.

⚠️ **Но «вид 0 для `0x2e` — это DubaiB16BIT» НЕ ДОКАЗАНО.** Таблицу
прыжков `@0x1a96f4` прочитать не удалось: в [33](33-tablicy-perehodov.md)
видно, что я взял не ту базу. Свидетельство пока одно — **замер**: эта
модель на планшете принята. Кандидатов по длине три (`3956Filter`,
`DubaiAFilter`, `DubaiB16BIT`).

Символы с их адресами ✅BIN:

| символ | адрес |
|---|---|
| `DLWeightLight3956Filter` | `0xd10c8` |
| `DLWeightLight3966MisTouch_13_13` | `0x23cf5c` |
| `DLWeightLightDubaiAFilter` | `0x119d4c` |
| `DLWeightLightDubaiB16BIT` | `0x387cb4` (582 580 Б) |
| `DLWeightLightDubaiB4_3_0_0MisTouch` | `0x1f42d8` |
| `DLWeightLightDubaiS200_116Filter` | `0x1ab654` |
| `DLWeightMis_3976ZS` | `0x285be0` |
| `ASPDLWeightLight3956PM` | `0x2ce864` |
| `ASPDLWeightLight3976PM` | `0x2fcd78` |

⚠️ **`DLWeightLight3956Filter` существует отдельно** — то есть для нашего
чипа есть и свой фильтр, и DubaiB. Какой выбирается видом `0` — решает
таблица прыжков; для `0x2e` это **не проверено** (таблица в декомпиляции
не развернулась: «Could not recover jumptable»).

## 32.4 Что из этого следует

1. `1111` — это **две возможные модели**: основной фильтр (вид `0`) и
   защита от ложных касаний (вид `1`), и они разные по символу.
2. Для нашего `0x2e` вид `1` — `DubaiB4_3_0_0MisTouch`; **8e3b4 ≠ 0x12321**:
   `0x12321` слов = 298 116 байт, а наш файл 582 580 байт = вид `0`.
3. Значит **число слов и длина тела не одно и то же**: тело всегда
   `0xc3568`, а слова занимают начало с `+0x60`.

## 32.5 Что остаётся

Таблица прыжков @`0x1a96f4` для вида `0` — не развёрнута. Это единственное
место, где ещё не установлено «какой именно символ грузится на `3956`».
⚠️ Пока не развёрнута — **не утверждать**, что это DubaiB16BIT «потому что
так совпало по размеру»; кандидатов на `0x2e` три (`3956Filter`,
`DubaiAFilter`, `DubaiB16BIT`).
