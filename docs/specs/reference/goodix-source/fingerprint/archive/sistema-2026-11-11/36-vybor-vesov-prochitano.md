# 36 — Выбор весов вида 0: прочитано до конца ✅BIN

Здесь закрывается то, что в [32](32-chip-i-modeli.md) и [35](35-vybor-vesov.md)
оставалось «вероятным».

## 36.1 Как нашлась база таблицы

В [34](34-adresa-fajl-i-obraz.md) я ошибался дважды: то читал `.text` с
`+0x10000`, то писал, что адрес = файловое смещение. Правильный ответ даёт
**сам код**:

```
63668: adrp x8, a9000
6366c: add  x8, x8, #0x6f4        ← база таблицы = 0xa96f4
63670: ldr  x9, [sp, #40]         ← индекс = chip − 0x16
63674: ldrsw x10, [x8, x9, lsl #2]
63678: add  x8, x10, x8           ← ЦЕЛЬ = база + смещение
6367c: br   x8
```

⚠️ Вот и ошибка прошлых заходов: цель считалась от **адреса инструкции**,
а не от **базы, загруженной в `x8`**. База — `0xa96f4` (в `.rodata`, где
адрес = файловое смещение).

## 36.2 Куда ведёт каждый чип

`target = 0xa96f4 + offset × 4`:

| чип | цель |
|---|---|
| `0x2b` (3626ZS1) | `0xa944c` |
| `0x2c` (3636ZS1) | `0xa8ca8` |
| `0x2d` (3988) | `0xa9138` |
| **`0x2e` (3956 — наш)** | **`0xa9528`** |
| `0x2f` (5658ZS3) | `0xa95e0` |
| `0x30` (3976ZS1) | `0xa9864` |
| прочие | `0xa8ca8` (общая ветвь) |

## 36.2a ⚠️ Позиция таблицы в файле не подтверждена

Таблица в `.rodata` по адресу `0xa96f4` даёт **не тот набор** смещений: для
чипов `0x17…0x2a` там лежат одинаковые значения, а по коду эта ветвь — на
`0xa8ca8` (код ошибки). Значит либо таблица лежит не по `0xa96f4`, либо
смещения `int32` с иным шагом. **Пока это не сверено, таблица считается
прочитанной только по коду** (36.1), а имена ветвей — нет.

## 36.3 Ветви

По коду у ветвей видны коды ошибок (`0x3eb`) и две пары констант:

```
63680: w8 = 0x0003d40 (250 688) ... ветвь 0x2c? см. ниже
63688: w9 = 0x238ed (145 581)  ← число слов 16-битной модели
636e0: w8 = 0x0003d40
636e8: w9 = 0x12321 (74 529)   ← число слов 8-битной модели
```

⚠️ `0x238ed` = **145 581** слово × 4 байта = **582 324** байта, а размер
`DLWeightLightDubaiB16BIT` по `readelf` — **582 580**: разница 256 байт
(64 слова). **Это не совпало** — значит либо число слов относится к
другому символу, либо у `DubaiB16BIT` в конце есть хвост. Пока считать
«слово в слово» нельзя.

`0x12321` = 74 529 слов = **298 116 байт** — ровно размеры «половинных»
символов (`3956Filter`, `DubaiAFilter`, `DubaiB4_3_0_0MisTouch` и др.).

## 36.4 Итог

✅ Для нашего чипа `0x2e`:
* **вид 0** ведёт в ветвь `0xa9528`;
* **вид 1** — `DLWeightLightDubaiB4_3_0_0MisTouch`, `0x12321` слов
  (= 298 116 Б), это доказано строго.

⚠️ **Вид 0 ещё не доказан по имени.** В ветви вида `0` у `memcpy` стоит
`adrp x8, d0000 / ldr x8, [x8, #3768]` — то есть адрес символа берётся из
**таблицы GOT** (`.data` @`0xd0f80 + 3768`), а не из литерала. Надо
прочитать слот `0xd1e98` в `.data` и сверить с `readelf -rW`: если там
`R_AARCH64_GLOB_DAT … DLWeightLightDubaiB16BIT`, имя закрыто.

⚠️ И проверка счёта: `0x238ed` слов = 582 324 Б, а `DubaiB16BIT` = 582 580 Б.
Расхождение 256 Б. Либо число слов не про этот символ, либо у символа есть
хвост (заголовок). **Это остаётся открытым.**

## 36.5 Что это значит

Наш Rust грузит **именно вид 0** (`DubaiB16BIT`) — и это **совпадает** с
тем, что сток выбирает для `0x2e`. Вид 1 в рабочем распознавании не
участвует: так называемая «защита от ложных касаний» — отдельная модель,
и грузить её вместо основной нельзя.
