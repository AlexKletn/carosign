# 37 — `hal_milan_select_model` целиком, по дизассемблеру ✅BIN

Функция — **на самом деле `0x635c8…0x639fc`** (в декомпиляции Ghidra она
подписана как «FUN_…» внутри `hal_milan_init_model`).

⚠️ Это ещё раз про адреса: **доверять `objdump` по целому файлу**, а не
именам из декомпиляции.

## 37.1 Сигнатура и рамки

```
635c8: hal_milan_select_model(void *куда, u32 *число_слов, u32 вид)
635ec: если (куда == 0) || (число_слов == 0) || (вид >= 2) → 0x3eb (1003)
63640: вид == 0 → таблица прыжков по чипу       @0xa96f4, база в x8 — 0xa96f4
63608: вид == 1 → три сравнения по чипу (ниже)
63990: выход с кодом в [x29,#-24]
```

Счёт предела на словах: `w8 = 0x0003d40` (**250 688**) — **верхняя граница
числа слов**; если `*число_слов > 250 688` → `0x3eb`.

## 37.2 Вид `0` (основной фильтр) — ветви по чипу

Каждая ветвь делает одно и то же в трёх строках:

```
w9 = <число слов>            (*число_слов = w9)
если w9 > 0x3d40 → 1003
x8 = <адрес символа из GOT>
memcpy(куда, x8, w9 * 4)
```

Ветви, которые видны целиком:

| ветвь @ | число слов | байт | откуда символ |
|---|---|---|---|
| `0x63680` | **`0x238ed` (145 581)** | ≈582 324 | **GOT** `[x8, #3472]` |
| `0x636e0` | `0x12321` (74 529) | 298 116 | GOT `[x8, #3472]` |
| `0x63860` | `0x12321` | 298 116 | GOT `[x8, #3976]` |
| `0x63920` | `0x12321` | 298 116 | GOT `[x8, #3296]` |

⚠️ Слоты GOT считаются от `x8 = adrp(.got)` — он загружается один раз выше
по функции; по дизассемблеру видно `adrp x8, d0000` и `ldr x8, [x8, #N]`.
Сверять с `readelf -rW`: смещения `#3472` = `0xd90`, `#3976` = `0xf88`,
`#3296` = `0xce0` — это слоты `0xd0d90` (`DubaiB16BIT`), `0xd0f88`
(`DubaiB4_3_0_0MisTouch`), `0xd0ce0` (`DLWeightMis_3976ZS`).

⚠️ **Но слоты посчитаны неверно:** `x8` — это `adrp`-страница, а не
`0xd0f80`. По коду надо взять `adrp x8, d0000` + `ldr x8, [x8, #3472]`,
то есть слот `0xd0d90` **только если** адрес страницы действительно
`0xd0000`. Это надо сверить по дизассемблеру в самой инструкции `adrp`
перед `ldr`, а не угадывать. **Пока имя символа у ветви `0x63680` не
подтверждено.**

✅ Здесь я прошлый раз прочитал верно: `mov w9, #0x38ed` +
`movk w9, #0x2, lsl #16` = **`0x238ed` = 145 581 слово**, а
`mov w8, #0xd40` + `movk w8, #0x3, lsl #16` = **`0x3d40` = 250 688** —
верхняя граница. То есть это **ветвь 16-битной модели**.

## 37.3 Вид `1` (защита от ложных касаний) ✅BIN

```
63808: вид == 1 (иначе выход)
63820: w9 = chip;  63824: w9 -= 0x2c
6382c…: сравнения:
        0x2c → DLWeightLight3966MisTouch_13_13      (@0x63xxx, 0x12321 слов)
        0x2e → DLWeightLightDubaiB4_3_0_0MisTouch    (GOT @0xd0f88)
        0x30 → DLWeightMis_3976ZS                    (GOT @0xd0ce0)
```

## 37.4 Разрешение таблицы прыжков — **не решено**

Таблица `@0xa96f4` читается, но её смещения при базе `0x6366c` дают цели в
**данных**, а не в коде. Перебор по `.rodata` на «правдоподобную» таблицу
даёт много ложных кандидатов (`0xa7830…`), каждый из которых даёт цель в
другое место внутри самой таблицы — то есть это **не настоящая таблица**,
а совпадение.

⚠️ Честно: **какой адрес ведёт у чипа `0x2e` — не установлено.**
Установлено другое: в **ветви `0x63680`** стоит число слов `0x238ed`
(145 581), а это размер **16-битной** модели; все прочие ветви дают
`0x12321` (74 529).

## 37.5 Что это меняет в выводе

Раз 16-битная ветвь есть (одна из нескольких), а все остальные — 8-битные,
раскладка такая:

* у **одного** из поддерживаемых чипов основной фильтр — 16-битный;
* у остальных — 8-битный;
* наш `0x2e` — тот самый случай с `DubaiB16BIT` (по замеру ✅MSR), и он
  **совпадает** с единственной 16-битной ветвью.

⚠️ Но «ветвь `0x63680` принадлежит `0x2e`» — **не доказано**. Нужна
таблица прыжков или проба: это уже замер, а он — при реализации.
