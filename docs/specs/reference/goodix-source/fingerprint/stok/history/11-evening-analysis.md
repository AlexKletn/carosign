## 1. Почему на касание приходит ровно одно событие

✅ Двоичное `libgf_hal.so` `@0x18174–0x18254`: `gf_hal_irq()` берёт общий
мьютекс и вызывает через таблицу устройства `+112`. По `@0x181a4` при
`g_…` равном нулю ставится ошибка `1010` и вызова нет. `@0x172e0–0x17334`:
`gf_hal_authenticate` при нулевом том же слове отдаёт `1010` без вызова, иначе
зовёт `+64`.

⚠️ **То есть сток тоже обрабатывает ОДНО событие на один край**, а не серию.
Наш клиент в этом не хуже стока. Значит различие не в повторе `1016` — эта
правка была попыткой не по адресу. В стоке событий на прогон много только
потому, что он долго висит в сеансе и на каждый край отвечает заново.

Остаётся вопрос «почему после первого касания нет следующего края». Здесь
упирается в две поломки ниже.

## 2. Прежний вывод про «нет событий» был мусорным

✅ Замер: после `LOAD_KEEP` и до любого касания у proba накоплено
`atomic_inc(tychki)` ≈ 2500 — края идут постоянно с `nl_ms=40`, потребителя
нет, `netlink_unicast` отбрасывает на забитой очереди. Похоже схема
«перезаряжаемый конец» даёт края без касания; это надо мерить, а не гадать.

✅ Замер (счётчик в ядре): после `LOAD_KEEP`, без пальца и без `1010`,
90 секунд — **ноль** краёв. То есть на холостом кристалле (питание, сброс,
`INIT`) событий нет, и счётчик это подтвердил.

## 3. Где рвётся наш путь на середине

✅ Замер: наш клиент падал с `No such file or directory (os error 2)` ещё до
подготовки сенсора. Файл модели (582 580 = `0x8e3b4`) на месте, хеш совпал,
`/dev/qseecom` на месте. Значит код `2` приходит не от `open` пути, а из
другого места (см. п. 4) — его надо ловить отдельно, а не приписывать файлу.

⚠️ Две перезагрузки подряд (`reboot` из SSH) дали **три разных адреса**
(`.129` → `.173` → `.122`) и потерю того, что лежало в `/tmp` (эталон HAL).
После каждой перезагрузки: `tools/spinel-najti-obshodom.sh`, `tools/spinel-fp-moduli.sh`.

## 4. Вторая поломка: приложение Goodix не поднялось

✅ Замер (журнал ядра, загрузка `5b857f36-…`): при `LOAD_KEEP` прошивка
сначала пробует поднять уже загруженное **`cmnlib64`**, чтобы завести образ
приложения:

```
spinel-fp: spinel-fp: cmnlib64: NOT loaded (rc=-2, id=0)
spinel-fp: spinel-fp: app_start on cmnlib64 image: -22
spinel-fp: spinel-fp: calling app_start
spinel-fp: spinel-fp: app_start failed: -22
spinel-fp: spinel-fp: probe with driver spinel-fp failed with error -22
```

В прошлый раз на этом же месте журнал после `-22` продолжался строкой
`app 'goodixfp' LOADED, id=5`: образ поднимался повторной попыткой из
`/firmware/image`. Всей сборке ядра это свойство плавающее: `cmnlib64`
`rc=-2` в обеих загрузках, а исход разный.

⚠️ Следствие: `proba` не довязан (`bound, step 8` была, но модуль ушёл с
`-22`), и Rust-клиент не нашёл ни `/dev/goodix_fp`, ни загруженного приложения.
Образы по хешу совпадают с `current_work/fingerprint-ref/ta/` (сверено).
