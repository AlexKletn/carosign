## Условие входа в `hal_milan_init_model` ✅BIN

`hal_milan_init_model` @`0x163324` начинается с `FUN_00165c3c` —
`GF_CHIP_3956`-серия:

```c
chip = g_hal_config[0];                 /* тело DETECT_SENSOR +0x60 */
ok = (chip == 0x16) || (chip - 0x2b < 4) || (chip == 0x30);
```

То есть **вход разрешён для**: `22` (`0x16`), `43, 44, 45, 46`
(`0x2b…0x2e`), `48` (`0x30`). Наш `46` — проходит ✅.

⚠️ Раньше это условие стояло как «не разобрано»: теперь оно прочитано,
и оно объясняет, почему при чужом чипе модель просто не грузится.

## Первая неверная попытка: таблица «мимо»

Таблица в `.rodata` по адресу `0xa96f4` даёт **не тот набор** смещений: для
чипов `0x17…0x2a` там лежат одинаковые значения, а по коду эта ветвь — на
`0xa8ca8` (код ошибки). Значит либо таблица лежит не по `0xa96f4`, либо
смещения `int32` с иным шагом. **Пока это не сверено, таблица считается
прочитанной только по коду** (36.1), а имена ветвей — нет.

## Разрешение таблицы прыжков — **не решено**

Таблица `@0xa96f4` читается, но её смещения при базе `0x6366c` дают цели в
**данных**, а не в коде. Перебор по `.rodata` на «правдоподобную» таблицу
даёт много ложных кандидатов (`0xa7830…`), каждый из которых даёт цель в
другое место внутри самой таблицы — то есть это **не настоящая таблица**,
а совпадение.

⚠️ Честно: **какой адрес ведёт у чипа `0x2e` — не установлено.**
Установлено другое: в **ветви `0x63680`** стоит число слов `0x238ed`
(145 581), а это размер **16-битной** модели; все прочие ветви дают
`0x12321` (74 529).

## Что сработало

✅ `target = база_таблицы (0xa96f4) + offset` — один раз, без `×4`.
После этого `0x2e` → `0x63680`, где `0x238ed` слов.

## Урок

Три подхода из четырёх давали «уверенный» ответ, который был неверным:
таблица читалась не по той базе, а потом не по тому масштабу. Спасло то,
что каждый шаг сверялся с **кодом** (`ldrsw` + `add` + `br`), а не с
«похоже на правду».
