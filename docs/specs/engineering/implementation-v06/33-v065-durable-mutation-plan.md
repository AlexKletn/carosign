# 33. v0.6.5 — durable immutable MutationPlan for Engine recovery

**Status:** normative logical storage schema v2, resolving a *representation gap* flagged in 28/10. **Not** a new physical TA state-query mechanism, not a template serializer. See `contracts/proto/carosign/storage/v1/storage.proto`.

## Plan and authority

`OperationBody::{Enrollment,Removal}` still owns an immutable validated in-memory plan. A matching `MutationRecord.plan` is REQUIRED in the **same durable transaction** that first writes `MUTATION_PREPARED`, and its bytes are immutable thereafter. `StoredValue.schema_version = 2` for records written by this baseline. The plan records the **full affected logical enrollment scope** at the time of authorization, not presumed physical sensor/TA internals. It includes a discriminator (`ENROLL_NEW|ENROLL_REPLACE|REMOVE`), pre-existing binding snapshots, the planned platform `new_enrollment_id`/generation (when applicable), and scope digest. Enrollment IDs are generated by the system before hardware dispatch.

Snapshot includes exact `EnrollmentRef(id,authenticator,generation)`, `SubjectRef(authority,subject)`, provider-opaque ref **digest** and provider format ID/version. On update, compare exact Registry snapshot under mutation scope lock; no implicit sorting, filtering, or lenient generation match. Canonical scope identity is `authority[16] || subject[16] || authenticator_id[16]`; snapshot entries are sorted bytewise by `(enrollment_id,generation)` and encoded using a versioned unambiguous length-delimited byte format to compute `affected_scope_digest = SHA256("bio-mutation-plan-v2" || scope || transition_u32BE || new_id_or_zeros || new_generation_u64BE || snapshot_count_u32BE || entries)`; each entry is `enrollment_id[16] || authenticator_id[16] || generation_u64BE || authority_id[16] || subject_id[16] || provider_ref_digest[32] || format_id_len_u16BE || format_id_utf8 || format_version_u32BE`. Only canonical supported format IDs <=128 bytes and bounded enrollment counts are accepted. Reject duplicate refs, wrong subject/authenticator, changed generation, zero IDs, malformed string or digest mismatch. The digest is an **integrity consistency checksum**, not a trust anchor or substitute for external anti-rollback.

The plan does not contain templates or private raw bytes. On creation, the future provider-opaque ref is not yet known. `DesiredState` therefore denotes a **predicate**: for new enroll a new platform enrollment is present with expected identity/generation and a *freshly verified* provider binding; for replace, original binding absent and new target present; for remove, target absent and all unaffected bindings unchanged. This is not a byte-for-byte prediction of unseen hardware data. The immutable plan is sufficient to tell the verifier **what to compare**, not to prove it happened.

## Recovery algorithm

1. Decode `StoredValue` with explicit version check, then require matching `MutationRecord.kind`, operation/subject/authenticator/epoch, `plan.transition`, IDs and scope digest. `mutation_scope_lock` and outbox must reference this same mutation. A plan with missing parts is **CorruptState**, not `NoChange`.
2. For phase `PREPARED` with no durable armed transition, confirm no persistent hardware mutation dispatched; release resources/challenge, metadata NoChange cleanup.
3. For phase >=`DISPATCH_ARMED`, never replay. Reconstruct the Engine operation from tagged kind + validated immutable plan. Reconcile using an **independent physical/hardware witness** with sufficient provenance, not Registry alone or worker's stale outcome.
4. Compare independently observed complete affected scope to the planned pre-state and desired predicate. The post predicate for a newly generated binding must be linked to the original mutation by a trusted physical/device query or witnessed authoritative provider storage transaction. If the new provider ref cannot be discovered/trusted after a crash, verdict = `Indeterminate`.
5. `DesiredStateConfirmed` and `PreStateConfirmed` retain distinct atomic transactions and cleanup sequence from 27/28. Partial replacement, changed unknown registration, absent preexisting binding or mixed state = `Indeterminate`. Goodix with no safe query remains `NeedsReconciliation`; the plan does **not** unlock it.

## Migration, limits, lifecycle

Newly created mutation plans are version 2. Existing v1 draft records that are already `COMPLETED` and fully validated with explicit `terminal_outcome` may be read by an explicitly audited migration. Any v1 `PREPARED`, `DISPATCH_ARMED`, `NEEDS_RECONCILIATION` or other nonterminal record **without complete plan** must remain quarantined until independent recovery or decommission. Never fabricate a v2 plan from only `expected_generation` and `target_enrollment`. A migration never silently sets Committed/NoChange.

Max snapshots = bounded configured enrollments per scoped authenticator, <=256; max serialized stored metadata = 64KiB. A provider format reference is compared as metadata but never interpreted by Core/Engine. Digest does not authorize worker or verify hardware.

## Conformance

R-01 v2 prepared record persists plan + lock + outbox/ID consistency; R-02 canonical encoding stable independent of host endian; R-03 missing plan in armed record blocks recovery; R-04 old and new fully absent in replace => Indeterminate; R-05 authoritative original state intact => NoChange; R-06 independently confirmed desired new binding => CAS Committed; R-07 malicious provider false query cannot prove pre; R-08 unknown original v1 partial record retains quarantine; R-09 digest/subject/format mismatch rejected; R-10 no templates/core matcher added.

### v0.6.6 explicit correction (supersedes v2 binding/encoding text above)

The v0.6.5 plan remains the **semantic** source of truth, but its v2 persisted schema cannot disambiguate provider-opaque vs scoped-vault custody or bind the selected old target to the digest. For current baseline, use v3 `BindingSnapshot.binding_kind`, `EnrollmentRecord.binding_kind`, `MutationPlanRecord.old_target` and canonical v3 digest in [34](34-v066-enrollment-command-projection.md). New records use `StoredValue.schema_version=3`; incomplete v2 records stay quarantined. The Runtime derives an explicit checked `CommandPlan` from this immutable plan + exact Registry binding under the scope lock. Adapter/worker never infer replacement from missing optional fields.
