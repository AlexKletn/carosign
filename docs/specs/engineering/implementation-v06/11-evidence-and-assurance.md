# 11. Evidence, proof verification and assurance evaluation

Семантика расширенного описания аутентификатора и событий захвата определена
в [документе 36](36-authenticator-types-and-events.md).

## Separate three layers

1. **Match result**: a provider assertion (`Matched` / `NotMatched`). A compromised software worker may lie.
2. **Evidence material**: opaque data or handles bound to the current operation, possibly hardware token.
3. **Accepted factor**: conclusion by independent trusted verifier/evaluator that evidence meets a specific consumer request. It is not automatic OS authorization.

`carosign.provider.v1` carries only evidence *reference* or bounded opaque token in provider channel when a verified secure transport requires it. Public `carosign.client.v1` never carries raw token, template or image.

## Key types and ports

```rust
pub struct EvidenceContext {
    pub operation_id: OperationId,
    pub subject: SubjectRef,
    pub authenticator: AuthenticatorRef,
    pub enrollment_generation: EnrollmentGeneration,
    pub purpose: VerificationPurpose,
    pub recipient: RecipientRef,
    pub challenge: ChallengeRef,
    pub deadline: BootDeadline,
}
pub trait EvidenceVerifier: Send + Sync {
    fn verify<'a>(&'a self,
        material: EvidenceMaterialRef,
        context: &'a EvidenceContext,
        requirements: &'a EvidenceRequirements,
    ) -> BoxFuture<'a, Result<EvidenceAssessment, EvidenceFailure>>;
}
```

`EvidenceMaterialRef` is an opaque short-lived handle retained in restricted EvidenceRouter. `ChallengeRef` refers to value created or accepted by the protected recipient or trusted authority; random nonce generated by unprivileged caller is not sufficient to make a KeyMint-compatible token. `EvidenceAssessment` is sealed internal result of verifier and signed/scoped to its provenance where required, never populated from provider manifest fields.

## Required checks

- Current operation ID, SubjectRef, recipient/purpose, authenticator/epoch and enrollment generation match.
- Challenge is fresh, one-use, and accepted by intended recipient.
- Evidence provenance, format, integrity, expiry and non-replay properties were actually checked by an authorized verifier.
- Hardware-backed claim requires hardware proof path, sensor input trust and template isolation **where independently established**; existence of QSEE/QTEE/TPM alone is insufficient.
- Changed boot trust state/firmware/profile generation invalidates assessment when its scope requires it.
- No provider assertion may expand required properties. Unknown properties are `Unverified` and fail policies that require them.

## Software verifier (GXFP/libfprint)

Software matcher success can be accepted for ordinary local login subject to configured software-trust policy. It cannot be promoted to hardware attestation or authorized KeyMint operation merely by wrapping it in a Rust type. The platform should distinguish `SoftwareAsserted` from a hardware-verifiable result in assessments and UI diagnostics.

## Hardware verifier (Goodix/Nord4)

Opaque hardware authentication tokens must be delivered to the **compatible** trusted verifier or protected key operation. If the token cannot be validated independently, return `UnsupportedEvidence` or `Unverified`; do not declare strict biometric class. On Nord4 the research document does not establish complete fingerprint→token→KeyMint chain in Veles; this remains an explicit [STOP condition](17-delta-and-open-evidence.md).

## Lifetime and replay

Evidence handle belongs to a single operation, auth subject, purpose and recipient, expires with operation/grant, and is consumed or invalidated after delivery attempt. On owner disconnect/cancel, zeroize/close material where possible; never reuse result for another PAM request. Evidence assessment invalidates on device epoch, enrollment generation, trusted configuration or recipient generation changes.

## Error taxonomy

`MalformedEvidence`, `UnsupportedFormat`, `WrongRecipient`, `ChallengeMismatch`, `Expired`, `Revoked`, `UnverifiedProvenance`, `IncompatibleAssurance`, `VerifierUnavailable`. All fail closed; do not convert to `NotMatched` because user feedback and security meaning differ.

## Reconciliation vs evidence

`EvidenceVerifier` evaluates **verification results**. `ReconciliationVerifier` checks **persistent mutation state**. They are separate ports and may use different hardware facilities. Successful biometric match does not prove a previously interrupted enrollment committed.

### v0.6.4 — matching locality does not classify evidence

Host/Match-on-Chip/TEE are **provider-internal choices**, not classes of trustworthy evidence. When a validated worker reports a scoped match without proof material, trusted Runtime creates a `ProviderAssertion` evidence handle, bound to the operation, subject, authorized enrollment set, worker/epoch, recipient, purpose and challenge. That assertion may be accepted only under the consumer's explicitly configured provider/software-trust policy; it never qualifies as independently hardware-backed evidence. An opaque token must be checked by a compatible verifier; any unverified token may not be promoted. This extends the prior section titled “Software verifier” to no-token hardware provider assertions. See [29](29-v064-provider-owned-matching.md).

## Владение и независимая оценка материала

<a id="matched-evidence-handoff"></a>

### Передача совпадения сеанса на независимую оценку

Актор одноразово передаёт проверенный `Matched` ограниченному владельцу материала после сверки операции, команды, работника, эпохи и разрешённого набора. Токен перемещается без сохранения исходной копии. Если регистрация не указана, требуется проверка ограничения сопоставления всему набору. После подтверждения приёма актор ставит один `ProviderMatched` с системным ID и удерживает эффект `VerifyEvidence` до передачи; повтор доставки эффекта не повторяет команду.

#### Точный договор

1. Добавить в Runtime типизированную одноразовую передачу `Matched` от
   удержанного актором проверенного наблюдения ограниченному владельцу
   материала. Право на такую передачу создаёт только сам владелец после
   фактического принятия материала; публичный конструктор из одного ID не
   создаёт подтверждения. Точный тип владения и место его конструктора
   должны обеспечить это правилом модулей, без публичного fallback.
2. До передачи повторно сверять операцию, работника, команду, эпоху,
   аутентификатор и закреплённый авторизованный набор. Если ответ назвал
   регистрацию, она обязана принадлежать набору с точным поколением. Если
   регистрация не указана, отдельная доверенная проверка ограниченности
   сопоставления всему переданному набору остаётся обязательной; выбор первой
   регистрации из набора запрещён.
3. Переносить токен во владельца по владению, не клонируя его. Не очищать
   удержанное наблюдение до подтверждённого приёма; при отказе материал
   остаётся у акторного владельца или безвозвратно очищается с безопасным
   отказом. После успешной передачи исходная копия не сохраняется. Размер,
   срок, отзыв и исчерпание проверяются до выдачи ссылки.
4. После принятия материала и проверки отсутствия отзыва актор ставит ровно
   один `ProviderMatched` с системным ID и сохраняет полученный шаг
   `VerifyEvidence` до передачи исполнителю. Очередь занята, актор занят,
   передача прервана или контрольное сообщение появилось раньше — повторяется
   только доставка удержанного шага, не чтение канала и не аппаратная команда.
   Отзыв до перехода уничтожает материал и не выдаёт положительный результат.
5. Исполнитель строит полный `EvidenceContext` исключительно из сохранённых
   авторизованных данных и проверенного сеанса и вызывает независимый
   `EvidencePort`. Нет проверенного получателя, вызова, регистрации там, где
   она обязательна, происхождения или допустимого оценщика — типизированный
   отказ. `Matched` и `ProviderAssertion` сами по себе не дают успех.
   Отзыв, срок и полномочия дополнительно проверяются перед фактической
   доставкой клиенту.
6. Сценарий без токена допускает только ограниченный `ProviderAssertion`
   согласно документу 29 после проверки происхождения и ограничения области.
   Аппаратная политика его не принимает. Этот ADR не определяет новые
   аппаратные протоколы, системные источники идентичности PAM или доверенного
   получателя и не создаёт production-проверяющего.

#### Проверки после принятия

В испытательном составе отдельный мок проходит `Matched → принятие материала
→ VerifyEvidence → независимая программная оценка`; параллельно проверяются
ошибочные операция, работник, эпоха, команда, регистрация/поколение и набор,
отсутствующий контекст, повтор, заполненная очередь, отмена и срок на каждой
границе, потеря владельца, очистка и сохранение эффекта при занятом
исполнителе. После любого неподтверждённого исхода успешный фактор не выдаётся.

<a id="evidence-port"></a>

### Проверка и отзыв ограниченного материала доказательства

`EvidencePort::evaluate` получает материал, полный проверенный контекст и требования; `invalidate` возвращает результат отзыва. Материал хранится ограниченное время в памяти, вне журнала. Владелец согласует одноразовую передачу и отзыв по операции и ссылке. Утверждение без токена создаётся доверенным Runtime из проверенного сеанса и разрешённой области. Положительная программная оценка требует явно разрешающей политики и независимой проверки. Аппаратная политика требует совместимого проверяющего. Перед доставкой повторно проверяются отзыв и срок.

#### Точный договор

1. Привести порт Runtime к документу 21: `evaluate(material, context,
   requirements)` возвращает оценку либо типизированный отказ;
   `invalidate(handle)` сообщает результат отзыва. Одновременно перевести
   исполнитель эффектов, адаптеры, фикстуры и тесты. Внешний protobuf не менять.
2. Передавать проверяющему контекст операции, субъекта, аутентификатора и
   эпохи, регистрации и поколения, цели, получателя, вызова и срока. Для
   утверждения без токена также сохранить привязку к разрешённому набору,
   работнику и эпохе, как требует документ 29. Неполный или устаревший
   контекст — отказ; ID из сообщения провайдера не является полномочием.
3. Ограниченный владелец материала выдаёт уникальную ссылку только после
   принятия материала и сохраняет его в памяти не дольше предусмотренного
   срока. Он ограничивает число и размер хранимых материалов существующими
   пределами спецификации, отказывает при исчерпании и не пишет их в журнал.
   Проверка и отзыв согласуются атомарно по операции и ссылке. Передача
   проверяющему одноразова; повторная передача и доставка после отзыва или
   срока запрещены. Потеря подтверждения не разрешает переиграть материал.
4. Отзыв, отмена, разрыв владельца, истечение срока и попытка доставки
   приводят к инвалидированию и очищению удерживаемых байтов. Подтверждение
   эффекта уничтожения допускается только после фактического освобождения
   материала соответствующим владельцем; ссылка без владения байтами сама по
   себе очистку не подтверждает. Ограничения очистки временных копий protobuf
   и чужого процесса отдельно документируются и проверяются.
5. Утверждение без токена создаёт только доверенный Runtime из проверенного
   сеанса и авторизованной области. Положительная оценка допускается только
   независимым проверяющим при явно разрешённой политике программного доверия.
   Для токена нужен совместимый проверяющий; флаг аппаратного пути или ответ
   самого работника не создаёт аппаратной гарантии. Отзыв полномочий и срок
   дополнительно проверяются перед фактической доставкой результата.

#### Проверки после принятия

Сквозной тест отдельного мока должен проверять отказ неверной регистрации,
поколения, субъекта, работника, эпохи, получателя, цели и вызова; повтор
материала, отзыв, истечение срока и отмену во время проверки; очистку и
отсутствие материала в публичном IPC и журналах. Отдельно проверить доступный
программной политике `ProviderAssertion` и отказ аппаратной политики для него.
Проверка положительного ответа после отзыва обязана отказать. Испытательные
утверждения и обработчики не доказывают аппаратную защиту.

<a id="evidence-slot-reuse"></a>

### Ограниченное повторное использование слотов доказательств

Внутренняя ссылка на материал связывает экземпляр владельца, монотонное поколение слота и ID операции и материала. Она не сериализуется. Поколение не переиспользуется и не переполняется циклически. Ёмкость освобождается после уничтожения байтов, завершения активной передачи и подтверждения актором. Устаревшая ссылка не действует на новое поколение даже при совпадении ID.

#### Точный договор

1. Сделать внутреннюю ссылку `EvidenceMaterialRef` непрозрачной возможностью,
   выдаваемой только ограниченным владельцем после принятия материала.
   Ссылка содержит идентичность экземпляра владельца, монотонное поколение
   слота этого экземпляра и текущие ID операции и материала. Прежний публичный
   конструктор произвольной ссылки удалить; wire Protobuf не менять. Такая
   ссылка подтверждает только происхождение выдачи, а не оценку или право.
2. Идентичность экземпляра представлять неповторяемой в пределах адресного
   пространства возможностью владения: старая живая ссылка удерживает свою
   идентичность, поэтому новый владелец не может стать ей равным даже при
   совпадении адреса, номера операции и ID материала. Ссылка не сериализуется,
   не публикуется клиенту и не восстанавливается после перезапуска. При
   межпроцессной проверке ссылка заменяется отдельным ограниченным каналом,
   а не сериализацией этой возможности; такой канал в этом ADR не задаётся.
3. Поколение назначается при каждом новом материале под блокировкой владельца,
   никогда не обнуляется и не повторяется в одном экземпляре. При исчерпании
   диапазона выдача прекращается с типизированным отказом, без wrap и сброса.
   Проверка ссылки, отзыв, уничтожение и освобождение места атомарно сверяют
   идентичность владельца, поколение и оба ID. Подмена любого поля — отказ.
4. Освобождать ёмкость можно только после подтверждённого уничтожения байтов,
   отсутствия активной выдачи проверяющему и принятия соответствующего шага
   актором. Если материал всё ещё удерживается, результат отзыва или handoff
   неизвестен, или актор не подтвердил уничтожение, место остаётся занятым.
   Смена одной только стадии на `Destroyed`, ID операции или вызов `Drop`
   составом не является достаточным основанием освободить место.
5. После освобождения материал прежнего поколения нельзя повторно получить,
   отозвать вместо нового или использовать для подтверждения его уничтожения,
   даже если оба ID совпали. Новая проверка может получить свободное место;
   одновременно активные материалы ограничены действующим пределом операций.
   Отзыв и срок продолжают работать до завершения передачи эффекта актору.
6. Изменения выполняются одновременно в владельце, портах `EvidencePort`,
   реестре, акторе и их адаптерах; никаких временных конструкторов произвольной
   возможности или fallback на прежнюю пару ID. Доверенный контекст,
   независимый проверяющий и доступ к аппаратному доказательству этим
   решением не создаются.

#### Проверки после принятия

Последовательно выполнить более 256 операций с подтверждённой очисткой;
одновременно занять предел и получить отказ. Проверить старую ссылку при той
же паре ID и новом поколении, другую операцию и другого владельца, конкуренцию
с отзывом/истечением/проверяющим/handoff, потерю владельца, переполнение
поколения и создание нового экземпляра после перезапуска. Нельзя возвращать
успех или повторно использовать материал после неопределённого уничтожения.
