# 36. Типы аутентификаторов, события захвата и свойства надёжности

Документ определяет семантику расширения общего, провайдерского и
клиентского контрактов. Номера новых полей и согласование расширения в
Protobuf утверждаются при реализации. Действующий профиль первого
Linux-выпуска сохраняет базовый обмен для отпечатков.

## Тип и возможности устройства

`type_id` обозначает модальность. На проводе он соответствует значению
`Modality`. Платформа ведёт закрытый словарь типов. Провайдер выбирает
значение из словаря при объявлении аутентификатора. Код отпечатка сохраняет
значение действующей схемы.

| Тип | Какая биометрия считывается |
|---|---|
| `Fingerprint` | Отпечаток пальца |
| `Face` | Лицо |
| `Iris` | Радужная оболочка глаза |
| `Voice` | Голос |

Сканирование сетчатки требует отдельного типа `Retina` при расширении
словаря. Добавление типа в словарь само по себе не включает поддержку
этого типа в сборке или политике.

Конкретный аутентификатор объявляет устойчивый `authenticator_id`,
`type_id`, доступные операции, способы взаимодействия, способы захвата,
необязательное размещение и поддерживаемые события. Платформа назначает
эпоху устройства и сверяет объявление с защищённым профилем. Список
`supported_events` задаёт подмножество словаря типа. Объявление возможностей
не подтверждает присутствие аппаратуры или её готовность.

| Поле | Что описывает | Примеры |
|---|---|---|
| `interaction_modes` | Действие пользователя | `Touch`, `Swipe`, `LookAtCamera`, `Speak` |
| `capture_methods` | Способ получения сигнала, если он известен | `Capacitive`, `Optical`, `Rgb`, `Infrared`, `Depth`, `Audio` |
| `placement` | Размещение считывателя, если оно известно | `UnderDisplay`, `SideButton`, `External` |
| `enrollment_stages` | Необязательное ожидаемое число образцов для записи отпечатка | 4 |
| `operations` | Допустимые для устройства операции | `Verify`, `Enroll`, `Remove` |
| `supported_events` | Подсказки, причины повтора и единицы прогресса | `Center(Finger)`, `PartialCapture`, `AcceptedSamples` |

`UnderDisplayOptical` сохраняется в базовом обмене. В расширенном описании
он раскладывается на `placement=UnderDisplay` и `capture_methods=[Optical]`.
Действие пользователя объявляется отдельно.

В текущем Linux-выпуске каталог передаёт все четыре кода модальности.
Проверка готовности для операций в этой сборке включена для отпечатков.
Если провайдер ещё не подтвердил возможности, каталог может вернуть
тип из защищённого профиля с пустым списком операций и признаком
недоступности.

## Универсальное событие операции

Публичное событие содержит `operation_id`, монотонный `sequence` и одну
типизированную полезную нагрузку. Номер назначает платформа в потоке
операции. Провайдер передаёт исходные наблюдения в рамках привязанных
операции, команды, работника и эпохи. Платформа проверяет их и формирует
публичный поток. Авторизация наблюдения и правила повтора остаются в
[документе 07](07-public-client-contract.md).

| Вариант | Поля и семантика |
|---|---|
| `Prompt` | Обязательная подсказка `{action, target}` |
| `CaptureRetry` | Необязательный `reason` и необязательный `prompt`. Текущая попытка захвата завершилась без пригодного образца. Операция может продолжаться |
| `Progress` | Одна единица значения. `Percent` от 0 до 100 либо `AcceptedSamples { accepted, required }`, где `0 ≤ accepted ≤ required` и `required > 0`. При записи счётчик накопительный на всю операцию, а `required` остаётся постоянным после первого события. Клиент не выводит из счётчика завершение операции |
| `StateChanged` | Фаза операции по автомату платформы. Примеры — ожидание пользователя, обработка, отмена |
| `Terminal` | Итог всей операции по действующему контракту. После него поток новых событий прекращается |
| `Gap` | Потеря части истории. Включает снимок и номер, с которого продолжается наблюдение |

Подсказка состоит из стабильно кодируемых действия и цели. Каждая пара
валидируется целиком. Таблица задаёт начальный словарь для типов.

| Тип | Допустимые подсказки | Допустимые причины повтора |
|---|---|---|
| `Fingerprint` | `Place(Finger)`, `Center(Finger)`, `Move(Finger)`, `Remove(Finger)`, `Swipe(Finger)` | `PoorQuality`, `PartialCapture`, `SwipeTooShort` |
| `Face` | `Center(Face)`, `LookAt(Camera)`, `HoldStill(Face)`, `ImproveLighting(Scene)` | `PoorQuality`, `PoorLighting`, `OutOfFrame`, `Motion` |
| `Iris` | `Align(Eye)`, `LookAt(Camera)`, `HoldStill(Eye)`, `ImproveLighting(Scene)` | `PoorQuality`, `PoorLighting`, `OutOfFrame`, `Motion` |
| `Voice` | `Speak(Voice)`, `SpeakLouder(Voice)`, `ReduceNoise(Environment)` | `PoorQuality`, `TooQuiet`, `BackgroundNoise` |

`PoorQuality` применим ко всем четырём типам. Причина может отсутствовать.
`SwipeTooShort` и `Swipe(Finger)` требуют объявленного `Swipe`.
События захвата ограничены возможностями конкретного аутентификатора.
Клиент локализует инструкции сам. Свободный текст провайдера не входит
в публичную полезную нагрузку.

```yaml
operation_id: "<идентификатор операции>"
sequence: 12
capture_retry:
  reason: PartialCapture
  prompt:
    action: Center
    target: Finger
```

`NoSample` завершает операцию без пригодного образца. `NotMatched` означает,
что пригодный образец сравнили и совпадения не нашли. Подозрение на подмену
обрабатывается доверенным контуром безопасности и политикой. Публичный
поток отдаёт только допустимый итог или безопасную общую подсказку.
Сырые кадры, аудио, шаблоны, токены, внутренние оценки качества и детали
детектора подмены не передаются в публичном потоке.

## Заявленные и подтверждённые свойства

Провайдер может объявить `assurance` в возможностях аутентификатора.
Это набор свойств с определённым смыслом, без общего числового рейтинга.
Начальные свойства:

- Поддержка обнаружения атак предъявления. Значения `Unknown`,
  `Unsupported`, `Declared`. Для `Declared` допускается список
  заявленных видов предъявления, например `PrintedPhoto` и `ScreenReplay`.
  Пустой список означает, что покрытие не уточнено.
- Хранение шаблонов. Используется существующий `TemplateCustody`.
- Условия захвата, если они выражены поддерживаемыми способами
  взаимодействия и причинами повторов. Эти сведения предназначены для UI.

На проводе `CapabilityDescriptor.assurance` содержит
`DeclaredAssurance`. Провайдер может передать его при обнаружении
устройства, в `PrebindDescription` или в `AuthenticatorReady`.
Если ответ о готовности содержит декларацию, каталог использует её.
Если поле в ответе отсутствует, каталог сохраняет декларацию,
полученную при обнаружении или до привязки.
Клиент получает декларацию в `ListAuthenticators` и `GetAuthenticator`.
Отсутствие поля означает, что сведений от провайдера нет. Для `Unknown`
и `Unsupported` список видов предъявления должен быть пустым.

Платформа хранит оценку отдельно от декларации. Для каждого свойства
оценка содержит статус `Unverified`, `Verified` или `Rejected` и ссылку
на основание оценки в доверенном контуре. `Verified` относится к точному
подтверждённому покрытию. Например, подтверждение защиты от фотографии
не распространяется на воспроизведение видео. `Rejected` означает, что
проверка установила несоответствие. `Unverified` используется при
отсутствующей, просроченной или неприменимой оценке.

Оценка привязана к аутентификатору, эпохе, версии защищённого профиля и
проверенной конфигурации. При изменении этой привязки оценка теряет силу
до повторной проверки. Отсутствующее или неподтверждённое свойство не
удовлетворяет политике, которая требует его подтверждения. Тип устройства,
способ захвата и декларация провайдера сами по себе не повышают уровень
доверия.

Подтверждение возможностей устройства и проверка доказательства конкретной
операции выполняются раздельно по [документу 11](11-evidence-and-assurance.md).
Для UI тип задаёт название и иконку, возможности — начальную инструкцию,
а политика — допустимость применения для конкретной цели. Если политика
предоставляет UI статус допустимости, статус формирует платформа.

## Совместимость и приёмка

Расширенный обмен требует явного согласования отдельно на границе с
провайдером и на границе с клиентом. Исходные значения перечислений и
номера полей сохраняются. В расширенном событии используется Protobuf
`oneof`. Поставщик и потребитель обязаны сверять форму, контекст и порядок
известных событий. Клиент с согласованным расширением пропускает
неизвестный вариант нагрузки с учётом его номера, неизвестную подсказку
пропускает, а неизвестную причину `CaptureRetry` отображает как общий
повтор. Пропуск не меняет итог или фазу операции.

На границе провайдера `WorkerHello.features` предлагает
`FEATURE_CAPTURE_FEEDBACK_V1`, а `Initialize.enabled_features` включает
его для сеанса. Провайдер объявляет варианты в
`AuthenticatorReady.capabilities.supported_events`. Для типизированного
кадра он передаёт `ProviderProgress.feedback`, оставляя базовые `kind` и
`percent` нулевыми. Платформа сверяет нагрузку с объявленными вариантами,
модальностью и способом взаимодействия привязанного устройства.

На публичной границе клиент предлагает `Hello.capture_feedback_v1`, а
`HelloAck.capture_feedback_v1` подтверждает расширение. После этого
`OperationEvent.feedback` содержит типизированный `CaptureFeedback`.
Внешний `EventKind` сохраняет базовое значение, поэтому клиент может
учесть номер даже для неизвестного варианта внутри `feedback`.

Для базового клиента платформенный адаптер передаёт существующие события
отпечатка, когда преобразование однозначно. `CaptureRetry` преобразуется
в `Retry`. Для подсказки без базового эквивалента передаётся `Working` с тем же номером. Фасад fprintd передаёт промежуточные
`EnrollStatus` и `VerifyStatus` с `done=false`. Для повторов он различает
слишком короткое проведение, необходимость центрировать или убрать палец
и общий повтор. Число этапов после `Claim` берётся из `enrollment_stages`.
Первый `AcceptedSamples` уточняет число этапов для текущей записи.
Адаптер публикует изменение `num-enroll-stages` перед событиями прогресса.
Каждый новый промежуточный образец даёт один `enroll-stage-passed`.
Последний этап учитывается через `enroll-completed` после фиксации
регистрации. Фасад использует значения от 1 до 128. Число кадров прогресса и повторов не ограничивает запись. Приём ограничен общим сроком операции и тайм-аутом ожидания очередного кадра.

Для UI, которому нужна обратная связь в реальном времени, публичный
канал наблюдения использует `ObserveOperation` на отдельном соединении.
Исходное соединение записи получает подсказки по мере захвата. Исходное
соединение проверки получает накопленные подсказки при доставке итога.
Число накопленных событий проверки ограничено размером истории с резервом
под завершающие события.

Минимальная приёмка включает:

1. Отпечаток с `PartialCapture` и `Center(Finger)`, лицо с
   `PoorLighting`, голос с `TooQuiet` в одном формате, с сохранением
   порядка и связи с операцией.
2. Отказ при неверной паре действия и цели, событии вне объявленных
   возможностей, чужой эпохе, повторном номере и сообщении после итога.
3. Совместимость базового клиента отпечатков, общую подсказку при
   неизвестной причине повтора и отсутствие ложного итога при пропуске.
4. Различимые состояния `CaptureRetry`, `NoSample` и `NotMatched`.
5. Провайдер объявляет обнаружение подмены и `Depth`, но без подтверждения
   политика с обязательным проверенным свойством отказывает. Проверенная
   оценка теряет силу при смене эпохи.

### Наблюдаемое состояние захвата

Устройство может объявить `CaptureEventState`. При согласованном
`CaptureFeedbackV1` провайдер передаёт `ProviderProgress.capture_state`
в событии `ProgressWorking` с нулевым процентом и без `feedback`.
`CaptureState.target` указывает объект захвата. Поля `present` и `needed`
независимы. Отсутствующее поле сохраняет текущее наблюдение. Платформа
проверяет заявленную возможность и соответствие цели захвата модальности.

Клиент получает состояние в `OperationEvent.capture_state`. Подсказки
остаются отдельными событиями. `CapabilityDescriptor.display_name` позволяет
поставщику сообщить короткое имя устройства для отображения.
