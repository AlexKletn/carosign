# 17. `carosign-provider-gxfp5130`: Rust worker internals

This is a **new architecture proposal** derived from the existing GXFP user-facing design, not a claim that current source already uses this layout. Retain useful Rust sensor/matcher crates and eliminate `gxfp-authd` as system policy owner over time.

## Independent workspace layout

```text
providers/gxfp5130/
  Cargo.toml
  crates/
    gxfp-hardware/            # protocol/device/session, platform IO
    gxfp-capture/             # acquisition, FDT, burst and quality
    gxfp-match/               # NCC / phase / hybrid / embeddings
    gxfp-template/            # template format, migration and protection
    gxfp-provider/            # maps hardware to carosign.provider.v1
  bins/
    bio-provider-gxfp5130/
```

## `gxfp-hardware/src`

`device.rs` (`/dev/gxfp` wrappers), `transport.rs` (sensor I/O), `tls.rs` (MCU TLS PSK session), `chicagohs.rs` (sensor profile), `activation.rs`, `calibration.rs`, `fdt.rs`, `interrupt.rs`, `recovery.rs`, `errors.rs`. All FFI/unsafe isolated to this crate and the Linux backend. PSK material never in logs or normal IPC.

## `gxfp-capture/src`

`capture.rs`, `burst.rs`, `fusion.rs`, `quality.rs`, `odometry.rs`, `coverage.rs`, `novelty.rs`, `frame.rs`. Capture sample is internal to worker; public events are only interaction/progress. Input geometry derived from device profile (80×64 currently observed) rather than hardcoded in Core.

## `gxfp-match/src`

`matcher.rs` (trait internal to provider, NOT global provider API), `ncc.rs`, `phase.rs`, `hybrid.rs`, `embedding.rs`, `model_runtime.rs`, `threshold_policy.rs`, `diagnostics.rs`. Threshold calibration/testing separate from OS authority. Goodix TA matching never uses this code.

## `gxfp-template/src`

`record.rs`, `schema.rs`, `codec.rs`, `compatibility.rs`, `encryption.rs`, `migration.rs`. Existing redb + AES-256-GCM and TPM-sealed secrets are separate concerns: provider templates can use platform delegated template/key port; releasing keyring password after match is **outside provider**. Avoid plaintext dev templates on normal prod paths.

## `gxfp-provider/src`

`main_adapter.rs`, `capabilities.rs`, `device_binding.rs`, `session_actor.rs`, `enrollment.rs`, `verification.rs`, `removal.rs`, `reconcile.rs`, `events.rs`, `cancel.rs`. Bound operation context from Runtime; worker cannot choose subject/authority or report hardware-proof level. Cancellation must reach control task while matcher blocks.

## Lifecycle and failure behavior

Start opens sensor after lease, reads PSK through scoped resource, activates/prime FDT once per managed session. `Verify` uses enrolled views + configurable matching; `Enroll` makes durable template through authorized delegated store. Worker restart may invalidate hardware session but must not silently regenerate PSK, rewrite templates or leak frame dumps. Diagnostic capture is separate permissioned tool.

## Product acceptance

1. install separately from carosignd;
2. enroll, verify, remove, reboot and reinstall without losing valid templates;
3. no raw frame/PSK outside worker;
4. software result classified accurately and no fake hardware evidence;
5. cancel/timeout, worker crash and device recovery follow common protocol;
6. algorithm/version migration does not silently compare incompatible templates.
