# 07. Runtime, scheduler, процессные состояния

## Три независимых state machine

**Worker:** `Installed → Selected → Starting → Negotiating → Binding → Ready → Draining/Recovering/Quarantined`.

**Device:** `Available → Reserved → Active → Quiescing → Available`; fault → `Uncertain → Recovering → Available/Unavailable`.

**Operation:** `Created → Authorizing → Queued → Acquiring → Running → Finalizing → Terminal`, плюс `CancellationRequested`. Перемешивать их в общий enum — ошибка.

## Actor модели

На одну аппаратную session — один actor с mailbox команд и отдельным control path для cancel/liveness. Блокирующий ioctl/TEE выполняется вне control task; request cancel должен доставляться даже при зависшем аппаратном вызове. Future cancellation не гарантирует прерывания kernel call.

## Планирование

Планировщик хранит bounded queues для каждого `ResourceSet`, выделяет lease атомарно и ограничивает один активный несовместимый доступ. Не делать предположение «один AuthenticatorId = один независимый датчик»: QSEE listener/TA и два логических аутентификатора могут делить ресурсы.

Предлагаемая политика: системный auth request имеет приоритет над диагностикой, но даже привилегированный клиент не получает бесконечную неотзываемую аренду. Starvation prevention и max wait — отдельно задаваемая политика ОС.

## Наблюдение и cancellation

Supervisor отслеживает process exit (на Linux предпочтительно pidfd), heartbeat отдельно от progress deadline, IPC closures, resource lease revocation. `WorkerAlive` != `DeviceHealthy`. После crash verification fail-closed; mutation journal → reconcile. При многократных crash — capped exponential backoff, затем Quarantined.

## Reboot

Процессные и UI grants не переживают reboot. Persistent MutationJournal открывается до активации конфликтующих enroll/remove. DeviceEpoch сбрасывается/меняется; ранее созданные request tokens и verification contexts инвалидируются. При unavailable provider registry остаётся, помечаясь недоступным.

## Граница жизни операции и сеанса

Операция принадлежит создавшему её клиентскому сеансу и аппаратному поколению.
После закрытия клиентского сеанса, завершения аппаратного сеанса или
перезагрузки прежняя операция не остаётся действующей, не возобновляется и не
может удерживать новую сессию как работающая операция. При потере клиента
платформа запускает отмену и уборку; потеря канала сама по себе не доказывает
завершение аппаратного вызова. Результат прежнего поколения нельзя принять в
новом сеансе.

Журнал возможной мутации и ограждение ресурса — отдельные состояния
восстановления, а не продолжение операции. Если изменение могло быть передано
провайдеру и его исход неизвестен, платформа сохраняет необходимые сведения и
открывает отдельную сверку. Такая запись не должна отображаться как активная
операция или безусловно блокировать всю платформу: ограничивается только
затронутая область, пока не подтверждён её безопасный исход. Для проверки,
не изменяющей постоянные данные, не создаётся постоянная блокировка сверки
мутации.

Наблюдённая проблема на TB371FC: после перезагрузки платформа сообщает об
области, ожидающей сверки, и аутентификатор недоступен; необходимо установить
происхождение записи и проверить, не удерживается ли прежняя операция или
избыточная область блокировки. Требование выше — целевое поведение; эта
запись сама по себе не доказывает причину конкретной блокировки.

## Композиция

В Linux может быть один основной демон + независимые providers; broker выделяется отдельно только при реальных требованиях безопасности. В Veles Runtime может размещаться в системной ячейке; scheduler/leases интегрируются с системными владельцами ресурсов.
