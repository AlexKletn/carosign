# 00. Источники, подтверждения и уровни решений

## Статус

Пакет собран из архитектурного обсуждения v0.1 → v0.4 и трёх материалов пользователя: `gxfp_user_facing.md`, `trust-anchor-auth-biometrics.md` и `fingerprint-docs-2026-11-11.tar.gz`. Временные метки в первичных документах сохранены как авторские; они не равны независимой перепроверке оборудования на дату сборки.

Уровни достоверности:

- **ОБСУЖДЕНО:** пользователь одобрил общее направление или прямо потребовал свойство.
- **ПРЕДЛОЖЕНО:** наш проектный вариант, подлежащий финальному утверждению.
- **ЗАДОКУМЕНТИРОВАНО В ИСХОДНИКЕ:** содержится в предоставленных материалах, но код и оборудование независимо не перепроверялись.
- **ПРОВЕРИТЬ:** не доказано на работающей системе.

## Что действительно продемонстрировали предыдущие проекты

### GXFP5130, MateBook

Описаны `gxfp-authd`, Unix IPC (`u32 LE` длина + bincode, один запрос на соединение), root-owned сенсор и секреты, `SO_PEERCRED`, `gxfp-pam`, `gxfp-authctl`, GUI и Wayland overlay, redb с AES-256-GCM, keyfile provider и отдельные `systemd-creds host+tpm2` secrets. Методы matching NCC/phase/embedding и параметры алгоритма специфичны для GXFP. Это существующие наработки пользователя, **не** нормативный API новой платформы.

Основные пробелы относительно новой архитектуры: авторизация enrollment отдельным сильным подтверждением, независимый Provider Protocol, устойчивые мутации, многоустройственный scheduler, оценка гарантий и изоляция алгоритмического worker.

### Goodix, TB371FC

Текущая спецификация исходного архива: `fingerprint/stok/*.md`; справочники: `fingerprint/tablicy/*.md`. Архивная история не должна подменять актуальную спецификацию. Описаны стек `spinel_fp_proba`, `spinel_qseecom`, listener/daemon, FS/GPFS/RPMB, HAL orchestration и команды Goodix TA. Стоковый HAL служит сравнительным эталоном, C-реализация — практически рабочим исследовательским прототипом, Rust — целевым продуктовым направлением.

В `stok/05-open-questions.md` остаётся нерешённой причина отсутствия следующего IRQ в прямом Rust-пути после первого события. Исторические измерения и этапы нельзя превращать в заявление о полностью завершённом нативном Rust matching. Нет необходимости переносить команды `1000…1111` в Core: они принадлежат Goodix provider.

### Nord 4 / Veles

`trust-anchor-auth-biometrics.md` **явно называется проектом и планом исследования**, а не принятой спецификацией либо доказательством защищённого пути. В документации имеются работающие диагностические вызовы QTEE/Keymaster, ранние Gatekeeper/отпечатковые эксперименты, модели grants/authority, журналы неопределённых мутаций и многочисленные синтетические тесты. Полная действующая цепочка «отпечаток → принятый hardware token → KeyMint» **не подтверждена**; доверенная поверхность и производственная интеграция не завершены.

## Что зафиксировано направлением продукта

1. Отдельный от Veles и обычного Linux-стека Core/Runtime.
2. Аппаратные providers устанавливаются независимо от Core/Runtime; платформа работает без них.
3. Providers — отдельные процессы с независимым lifecycle.
4. Provider API — межпроцессный языково-независимый протокол; Rust не является обязательным для авторов providers.
5. `libfprint` подключается через worker, не через форк Core; `fprintd` compatibility отделена.
6. Matching и решение о системной авторизации разделены; доверие к evidence не определяется одним только manifest.
7. Работа с TEE/TPM — optional infrastructure, не обязательное свойство Core.

## Предложено, но пока не ратифицировано

- Названия `carosign.client.v1`, `carosign.provider.v1`, `carosign.resources.v1` и др.
- Protobuf, `SOCK_SEQPACKET`, 64 KiB лимит control packet, таблицы ошибок и конкретные fields.
- Конкретный формат registry/journal и выбор системы хранения.
- Один worker на устройство как default; уровни доверия поставщиков; политики обновления, модель доставки firmware.
- Полный API поверхности взаимодействия, политика приоритетов и конкретная модель verifier.
