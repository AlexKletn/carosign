# ADR: точный wire управляющего канала посредника ресурсов

**Статус: проект для рассмотрения; не принят и не реализован.**

**Решение владельца проекта:** выбран вариант B — сохранять действующую
спецификацию и не добавлять передачу `SCM_RIGHTS` от брокера к демону по
управляющему каналу. Это решение относится только к границе FD: оно не
принимает предлагаемые ниже схему, номера полей, запуск, доверенные источники
или восстановление. До отдельного решения любые FD на проектируемом
управляющем канале запрещены; полученные дескрипторы необходимо закрыть.

Основание: `09-device-and-broker.md`, `13-limits-errors-and-observability.md`,
`20-protobuf-wire-validation.md`, `21-internal-port-signatures.md`,
`26-mediated-broker-v1.md`, принятые ADR жизненного цикла ресурсов и
`Quiescing`; предлагаемый `adr-broker-control-proposed.md`. Этот документ
уточняет предложенный договор и **не изменяет** действующий `carosign.broker.v1`.

## Требующее отдельного решения расхождение

Документ 09 разрешает `SCM_RIGHTS` на `BindAuthenticator`, а документ 32
добавляет ограниченное исключение для bulk на уже делегированном
`carosign.broker.v1`. Если отдельный брокер передаёт выданные FD владельцу
`carosignd`, нужен ещё один переход FD, не определённый действующим wire.
Нельзя незаметно считать его разрешённым или выдавать за `BindAuthenticator`.

**Невыбранное предложение A:** разрешить единственное дополнительное `SCM_RIGHTS` на
успешном `DelegateResult` ниже, только от доверенного брокера доверенному
составу. Последующая передача работнику остаётся исключительно в
`BindAuthenticator`. Проверка точной выдачи, ролей и идентичности нужна на
обеих границах. Это новое исключение из документа 09 требует явного принятия.

**Выбранный вариант B:** не передавать FD на управляющем канале и определить отдельный
доверенный механизм их передачи владельцу `BindAuthenticator`; такой механизм
пока не определён и требует своего договора и доказательства целостности.
Команды, которым требуется передача FD, **недоступны** до принятия и реализации
другого механизма. Сохранение варианта B не разрешает новый wire-договор.

### Что покрывает действующий `BindAuthenticator`

Документы 09 и 26 задают место передачи разрешённых FD работнику и их проверку:
брокер закрепляет связь лизинга, работника, ресурса и роли, а Provider Manager
проверяет её при передаче. Для `MEDIATED_SERVICE` документ 26 также требует,
чтобы брокер создал частную пару сокетов и удерживал свой конец. Эти требования
**не определяют**, как при раздельных процессах брокер и отправитель
`BindAuthenticator` получают в одном процессе требуемый FD без дополнительного
`SCM_RIGHTS`. Само наличие слота и запись лизинга не переносят дескриптор и не
подтверждают его происхождение. Прямое открытие `/dev` по пути, `SO_PEERCRED`,
`/proc` или вывод доверия из root не являются уже согласованным решением.

Один возможный предмет дальнейшего разбора — доверенный единый отправитель
`BindAuthenticator`, имеющий разрешённые дескрипторы локально и владеющий
порядком кадров provider-соединения. Нужно отдельно определить, каким
спецификационно допустимым способом ему предоставляются сам provider-канал,
проверенные ресурсы и полномочия, как ограничивается единственный писатель,
как предотвращается повтор после неопределённой отправки и как восстанавливается
посредник. Это направление поиска, **не утверждённая архитектура и не
доказанный механизм**. Без такого решения не добавлять делегирование FD и не
объявлять production-провайдера доступным.

## Граница доверия и запуск

Один унаследованный `AF_UNIX/SOCK_SEQPACKET` соединяет системный состав
платформы с отдельным посредником. Это не открытый путь в файловой системе,
не сокет работника и не делегированный `carosign.broker.v1`. Состав и брокер
удостоверяются отдельным системным механизмом запуска и привязки канала;
`SO_PEERCRED`, открытый FD, UID, nonce, номер операции и записи БД сами по
себе авторизацию не создают. До реализации такого механизма production-канал
не активируется. Тестовый процесс может иметь явно подставную политику,
но его ответы не свидетельствуют об аппаратной безопасности.

Ниже указаны **предлагаемые** точные поля для ревью. Они будут иметь силу
только после отдельного принятия этого ADR. Показанный в проектной схеме
`DelegateResult` сам по себе не разрешает передачу дескрипторов; вариант A
владельцем не выбран.
Внешние `.proto` и исходный код этим предложением не меняются.

## Предлагаемый Protobuf 1.0

Файл после принятия: `contracts/proto/carosign/broker_control/v1/control.proto`;
package `carosign.broker_control.v1`. Один `ControlFrame` — один пакет seqpacket,
сырой Protobuf без префикса, не более 65536 байт. Номера ниже не относятся к
существующему `carosign.broker.v1`. Любое новое поле или версия требуют review.

```proto
syntax = "proto3";
package carosign.broker_control.v1;
import "carosign/common/v1/common.proto";
import "carosign/provider/v1/provider.proto";

message ControlFrame {
  uint32 major = 1;              // ровно 1
  uint32 minor = 2;              // ровно 0
  uint64 frame_seq = 3;          // с 1, последовательно по направлению
  bytes request_id = 4;          // 16 байт, не все нулевые; пусто для Hello
  oneof payload {
    Hello hello = 10;
    Acquire acquire = 11;
    AcquireResult acquire_result = 12;
    Delegate delegate = 13;
    DelegateResult delegate_result = 14;
    Quiesce quiesce = 15;
    QuiesceResult quiesce_result = 16;
    Release release = 17;
    ReleaseResult release_result = 18;
    Revoke revoke = 19;
    RevokeResult revoke_result = 20;
    GetState get_state = 21;
    StateResult state_result = 22;
    Fault fault = 23;
  }
}
message Hello {
  bytes instance_id = 1;         // 16 ненулевых байт, не полномочие
  bytes boot_id = 2;             // 16 ненулевых байт, не полномочие
}
message Owner {
  bytes operation_id = 1;        // 16 ненулевых байт
  bytes worker_instance_id = 2;  // 16 ненулевых байт
  bytes authenticator_id = 3;    // 16 ненулевых байт
  uint64 device_epoch = 4;       // ненулевая
}
enum AccessMode {
  ACCESS_UNSPECIFIED = 0;
  ACCESS_EXCLUSIVE = 1;
  ACCESS_SHARED_READ = 2;
  ACCESS_MEDIATED = 3;
}
message Claim { bytes resource_id = 1; AccessMode mode = 2; }
message Scope {
  bytes lease_id = 1;            // 16 ненулевых байт
  Owner owner = 2;
  repeated Claim claims = 3;    // 1..8, строго по байтам resource_id
}
message Acquire {
  Owner owner = 1;
  repeated Claim claims = 2;    // те же ограничения
  bytes profile_id = 3;         // 16 ненулевых байт
  bytes policy_decision_ref = 4;// 16 ненулевых байт; не bearer право
}
message AcquireResult {
  oneof result { Scope granted = 1; carosign.common.v1.Error refused = 2; }
}
message ApprovedSlot {
  bytes resource_id = 1;        // входит в scope
  carosign.provider.v1.FdRole role = 2;
}
message Delegate { Scope scope = 1; repeated ApprovedSlot slots = 2; }
message DelegateResult {
  Scope scope = 1;
  repeated carosign.provider.v1.FdSlot slots = 2;
  carosign.common.v1.Error error = 3; // если задан, scope/slots отсутствуют
}
message Quiesce { Scope scope = 1; bytes fence_id = 2; }
message QuiesceResult {
  Scope scope = 1; bytes fence_id = 2; bytes quiesced_ref = 3;
  carosign.common.v1.Error error = 4;
}
message Release {
  Scope scope = 1; bytes fence_id = 2; bytes quiesced_ref = 3;
}
message ReleaseResult {
  Scope scope = 1; bytes fence_id = 2; bytes released_ref = 3;
  carosign.common.v1.Error error = 4;
}
message Revoke { Scope scope = 1; }
message RevokeResult { Scope scope = 1; carosign.common.v1.Error error = 2; }
message GetState { Scope scope = 1; }
enum LeaseState {
  LEASE_UNSPECIFIED = 0; LEASE_ACTIVE = 1; LEASE_QUIESCING = 2;
  LEASE_UNCERTAIN = 3; LEASE_RECOVERING = 4; LEASE_UNAVAILABLE = 5;
}
message StateResult {
  Scope scope = 1; LeaseState state = 2; carosign.common.v1.Error error = 3;
}
message Fault { carosign.common.v1.Error error = 1; }
```

`fence_id`, `quiesced_ref`, `released_ref` — каждый 16 ненулевых байт;
`fence_id` создаёт уполномоченный владелец ограждения, refs — брокер после
соответствующего подтверждения. Они не являются bearer capabilities. Брокер
сверяет выдачу и стадию с собственным защищённым состоянием; содержание wire
не может создать `Quiesced` или `Released` в доверенном Rust-порту само по себе.
Источники генерации, полномочий и физического свидетельства — отдельные порты.

## Строгий разбор и FD

- Первые сообщения обеих сторон — `Hello`, seq=1, пустой request_id; до обоих
  Hello никаких команд. Состав сверяет boot/instance с доверенным запуском.
  Первые Hello по 5-секундному пределу, как для provider bootstrap.
- Затем клиент посылает только запросы, брокер — соответствующие ответы с тем
  же request_id. В 1.0 предлагается **один незавершённый запрос на соединение**.
  Каждый request_id равен первым восьми байтам `instance_id` отправителя
  `Hello`, конкатенированным с восьмибайтовым номером `frame_seq` этого запроса
  в big-endian; ответ копирует его целиком. Это доказывает неповторяемость ID
  внутри соединения без неограниченного списка, но не удостоверяет отправителя.
  Счётчик не переполняется: до переполнения соединение закрывается. Новый
  instance_id выдаётся доверенным составом из безопасного источника, а не
  выводится из времени или UID; ошибка источника запрещает новый канал.
- Каждая обязательная вложенная структура присутствует; ID ровно 16 ненулевых
  байт, enum zero/unknown запрещён, строки claims отсортированы, дубли ID
  запрещены, пустой или более восьми ресурсов — отказ до действия. Эпоха
  больше нуля. Ошибка — ненулевой известный `ErrorCode`, safe_message не более
  256 байт и без секретов. У успешного ответа error отсутствует; scope и refs
  обязательны по типу. У отказа никакие scope, refs или slots не выдаются.
- `Fault` допустим только в ответ на текущий запрос с тем же request_id;
  после него соединение закрывается. При асинхронной аварии без запроса брокер
  закрывает канал, не придумывая request_id. Ответ, поступивший после закрытия
  или относящийся к предыдущему соединению, не возвращается актору как факт.
- Для `AcquireResult.refused` до начала выдачи допустимы `ERROR_BUSY`,
  `ERROR_UNAUTHORIZED`, `ERROR_GRANT_REVOKED`, `ERROR_SCOPE_MISMATCH`,
  `ERROR_UNAVAILABLE`, `ERROR_UNSUPPORTED`. Состояние после возможного начала
  действия нельзя кодировать как доказанную невыдачу: канал закрывается либо
  возвращает `ERROR_RESOURCE_UNCERTAIN`/`ERROR_BROKER_FAILED` с консервативной
  блокировкой. Для прочих отказов разрешены эти же коды и `ERROR_TIMEOUT`;
  `TIMEOUT` после возможного начала также означает неопределённость. Другие
  коды для ответов этого канала отвергаются как нарушение протокола.
- Для безопасности обязательны отказ на неизвестные поля, дубли singular и
  oneof, неверный wire type и превышение вложенности до Protobuf decode;
  простое игнорирование неизвестного поля декодером не подходит. Разрыв,
  `MSG_TRUNC`, `MSG_CTRUNC`, нарушение направления/seq/корреляции, повтор,
  лишний или отсутствующий FD закрывают канал; все полученные FD закрываются.
- В невыбранном предложении A только успешный `DelegateResult` нёс бы 1..8 FD, ровно
  число `slots`; индексы составляют `[0,n)`, роли допустимы, `(resource,role)`
  разрешены профилем и активной выдачей. Повтор ресурса по умолчанию запрещён;
  разрешение повтора требует отдельной политики. FD получаются с CLOEXEC,
  проверяются тип, конкретная идентичность и принадлежность подтверждённой
  записи брокера; неизвестная роль или нарушение закрывают **все** FD.
  Остальные кадры несли бы ноль FD. При выбранном варианте B **все кадры
  управляющего канала несут ноль FD**; делегирование, которому необходимы
  FD, не реализуется до отдельного утверждения механизма. Отправка FD работнику
  по-прежнему допускается только в provider `BindAuthenticator`.
- Значение `policy_decision_ref` проверяется доверенным источником независимо
  при каждом критическом запросе; право не возникает из данных wire. Не писать
  в журнал токены, полные кадры, секреты и имена пользователей.

## Состояния и сбои

1. `Acquire` допускается только после независимой проверки действующих
   политики, профиля, процесса работника и эпохи; вся область берётся атомарно.
   Результат `granted` допускается только после фактической полной выдачи и
   назначенного брокером ID. `BUSY`/`UNAUTHORIZED`/`UNAVAILABLE` до начала не
   равны подтверждённой выдаче; частичного успеха нет.
2. `Delegate` требует Active, полного совпадения области и действующих прав.
   Брокер фиксирует связь lease, worker, authenticator, epoch, resource, role,
   fd identity **до** передачи. Утерянный ответ или FD после возможной передачи
   означает неопределённость, а не повторное делегирование.
3. До `Quiesce` состав синхронно ставит ограждение `Quiescing` на полную
   выдачу. Подтверждение покоя даёт только независимый утверждённый адаптер.
   `QuiesceResult` с ref не освобождает ресурс. Смерть работника, закрытие FD
   и данные от него физический покой не доказывают.
4. `Release` возможен только после подтверждённого Quiesce с тем же scope,
   fence и ref; ref потребляется один раз. Только проверенный успешный ответ
   даёт владельцу одноразовый `Released`, связанный с экземпляром ограждения;
   он снимает ровно это ограждение. `Revoke` запрещает последующую передачу,
   но не подтверждает физическую остановку или release.
5. До системного вызова send локальная невозможность отправки — доказанная
   неотправка; после возможной передачи/потерянного ответа/timeout исход
   неизвестен. В 1.0 автоматический повтор начатого Acquire, Delegate,
   Quiesce, Release или Revoke запрещён. Состояние остаётся ограждённым,
   результат доверенному актору доставляется отдельно. `GetState` — только
   диагностика текущего брокера; сам по себе не является независимым
   физическим свидетельством и не снимает карантин.
6. После перезапуска брокера либо платформы пустой реестр не освобождает
   прежние ресурсы. Необходимо восстановить область неопределённости из
   защищённого устойчивого системного источника и провести независимую
   проверку. Формат устойчивых свидетельств и его авторитет **не определены
   этим документом**; без принятого решения и реализованного восстановления
   production Acquire после сбоя остаётся закрыт, даже для нуля текущих записей.

## Приёмка

До подключения к штатному составу нужны fixture успешной и отказанной выдачи,
двух одновременных SharedRead и Quiescing, неверных owner/epoch/mode/ref,
проверки всех вариантов FD, ошибки частичной выдачи и дубликатов полей;
процессные тесты убийства обеих сторон до и после каждой передачи, потери ACK,
смены эпохи, заполненного сокета и перезапуска; независимый C/Rust разбор тех
же байтов. Тест с имитацией policy и устройства не доказывает физический покой.
Отдельно должны быть представлены конкретный системный источник доверенной
политики и идентичности, устойчивое восстановление и защищённый источник
hardware quiescence для каждого профиля. Без них production остаётся закрыт.
