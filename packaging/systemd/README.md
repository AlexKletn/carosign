# Системная служба CaroSign для Linux

Файлы в этом каталоге — состав службы для проверки на отдельной установленной
Linux-системе. Файл `carosignd.service` запускает `/usr/bin/carosignd`,
создаёт `/run/carosignd` и `/var/lib/carosign`; unit поддерживает явное
включение администратором. Пакетный preset оставляет оба юнита отключёнными
по умолчанию.
`carosignd` публикует клиентский сокет с режимом `0666` и проверяет
полномочия каждого запроса. Адаптер D-Bus работает от root, получает UID
вызывающего от системной шины и отдельно проверяет его полномочия.

Администратор устанавливает unit в `/usr/lib/systemd/system/carosignd.service`,
настройки — в `/etc/carosign/carosignd.conf`. Настройки и каталог
должны принадлежать root и не быть доступны на запись другим пользователям.
Путь `socket` должен оставаться внутри `/run/carosignd`, чтобы systemd удалял
сокет при остановке или перезапуске службы. Нельзя включать сохранение
RuntimeDirectory между запусками: слушатель не удаляет старый файл сокета.

При первом запуске systemd создаёт каталоги состояния и сокета. Служба
создаёт отсутствующую базу и штатную политику `/etc/carosign/policy.conf`.
Начальная политика разрешает только чтение инвентаря пользователю root.
В режиме обнаружения служба также создаёт пустой список
`/etc/carosign/providers.conf`. Этого достаточно для запуска без провайдеров.

Для подключения оборудования настройте список публикаций или укажите
явный профиль согласно `linux-provider-profile.md` в документации пакета.
Доступ пользователей и биометрические операции требуют явных правил
политики. Если выбран другой путь к политике, подготовьте этот файл
перед запуском.

**Проблема первого запуска с аппаратным провайдером.** Если в конфигурации
задан `resource_fence_store`, служба ожидает, что база ограждений уже
существует. Пакет и служба не создают её автоматически. Без неё
`carosignd` завершает запуск с сообщением «хранилище ограждений не защищено».
При новой установке администратору приходится создать базу явно, указав путь
из `resource_fence_store`:

```sh
carosignd init-resource-fences /var/lib/carosign/resource-fences.redb
```

Исправление должно различать первую установку и потерю ранее существовавшей
базы. Во втором случае отказ защищает от повторной выдачи ресурса, состояние
которого осталось неизвестным.

```sh
systemctl daemon-reload
systemctl start carosignd.service
systemctl status carosignd.service
```

Ручная команда `carosignd init-store /абсолютный/путь` доступна для
предварительной инициализации. Существующая база проходит проверку при запуске.
После проверки на целевой системе администратор может выполнить
`systemctl enable carosignd.service`. Установка unit не меняет файлы PAM и
не активирует адаптер fprintd. Для ручного запуска совместимого адаптера
установите `carosign-fprintd.service` в каталог systemd, а
`carosign-fprintd.conf` — в `/usr/share/dbus-1/system.d/`. Системная шина
должна перечитать настройки. Затем администратор может запустить
`carosign-fprintd.service`. Этот адаптер занимает имя `net.reactivated.Fprint`
и несовместим с одновременной работой обычного `fprintd.service`.
В политике демона нужны разрешения для root-клиента и целевых пользователей.
Установка не подменяет D-Bus activation и не переключает системный fprintd.

Чистый запуск пакета с пустым каталогом проверяется командой
`sh tools/test-linux-systemd.sh [ядро]` на Arch Linux x86-64. Тест собирает
нативный пакет из того же установочного рецепта, устанавливает его в
отдельный корень через `pacman` и загружает этот корень в QEMU с systemd
в роли PID 1. Проверяются preset, создание новой базы, запуск,
создание политики и списка провайдеров, перезапуск, очистка runtime-каталога
и отказ при повреждённой базе.

Регистрация, проверка и удаление прошли отдельное сквозное испытание
с тестовым провайдером. Для TB371FC остаётся аппаратная приёмка с запасным
способом входа.
